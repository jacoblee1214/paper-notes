## 1. 한 줄 요약

한 대의 원격 GPU가 여러 로봇의 π0.5 정책 추론을 배치로 처리할 때, "어느 로봇을 이번 배치에 넣을지"를 **로봇 쪽 행동 큐의 상태를 서버에서 거울처럼 추적하며 고르는 스케줄링 문제**로 보고, 1단계 Lookahead 스케줄러(LA)와 서빙 엔진 Armory를 제안합니다(§1, §3).

## 2. 문제 설정 (§2)

- **행동 청킹과 비동기 실행.** 정책은 관측 o_t로 길이 H의 청크 A_t를 만듭니다. 로봇은 제어 주파수 f_c로 행동 인덱스를 하나씩 올리며 실행하고, 비동기에서는 다음 청크 추론이 현재 청크 실행과 겹칩니다(§2, 그림 2). 실행 인덱스는 단조 증가해야 합니다([12]).
- **실행 지평 [H_min, H_max].** 로봇은 청크의 앞 H_max개만 쓰고, 다음 요청은 H_min 개를 실행한 뒤에야 서비스됩니다. 최적 구간은 과제에 따라 다르다고 주장합니다(그림 3a).
- **지연 d = d_obs + d_infer + d_action.** 서버가 배치를 키우면 d_infer가 커집니다(§2).
- **기아(starvation).** 로봇이 실행할 행동이 없는 제어 스텝. 기아가 과제 성능을 떨어뜨리고 그 정도는 과제마다 다르다고 가설을 세우고 그림 3b로 검증합니다(§2).
- **이질성.** 빠른(fast) 로봇은 동적 과제(턴테이블 정리)로 H_max가 짧고, 느린(slow) 로봇은 준정적 과제(벽돌 분류)로 H_max가 깁니다. "빠르다"는 로봇이 움직이는 속도가 아니라 **청크를 소모하는 속도**입니다(§4.1).

## 3. 방법 (§3)

### 3.1 MDP (§3.1, 식 1–11)

- 로봇 j마다 i_j(마지막 실행 인덱스), î_j(서버가 받은 마지막 인덱스), 청크 큐 Q_j(청크 c = (i_start, h_j, t_arr))를 추적합니다(식 1–5). 상태 s_k = (t_k, i_j, î_j, Q_j).
- 전이: 배치 B_k를 고르면 추론은 t_{k+1} = t_k + d̃_infer(|B_k|)에 끝나고(식 6), 서빙된 로봇의 새 청크가 Q_j에 추가됩니다(식 7). 모든 로봇은 f_c로 진행하되 도착한 청크가 인덱스를 덮고 있을 때만 i_j가 1 증가합니다(식 8). î_j는 서버에 도착한 가장 최근 스텝으로 갱신됩니다(식 9).
- 보상(식 10): R(s_k, B_k) = (1/f_c) Σ_j w_j Δi_j(s_k, B_k), 즉 에폭 동안 **기아가 아닌 제어 스텝의 가중 합**. w_j는 과제별 가중치입니다.
- 목표(식 11): 기대 보상 합을 최대화하는 정책.

### 3.2 Lookahead (§3.2, 식 12–13, 부록 A.1)

- 정확한 계획은 분기 폭발 때문에 불가하므로, 길이 L의 스케줄 S = ((s_0, B_0), …, (s_{L−1}, B_{L−1}))를 모두 나열해 거울로 굴려 보고, 점수가 최고인 스케줄의 **첫 배치 B_0만** 보냅니다(식 12).
- 점수(식 13): Score(S) = Σ_ℓ R(s_ℓ, B_ℓ) / d_infer(|B_ℓ|), 즉 **GPU 시간당 보상**.
- 비교 대상: **RR**(포인터를 돌며 최대 b개를 채움)과 **EDF**(큐가 가장 먼저 바닥나는 b개).
- 실험에서는 L = 1(부록 A.5), 점수는 "스케줄 시작 시각부터 **1초 창** 안의 총 실행 로봇 시간"이라고 부록 A.1 마지막 문단이 적습니다. 후보 배치는 "휴리스틱으로 가지치기"합니다.

> 주의: 식 10은 한 전이 [t_k, t_{k+1}] 동안의 실행 스텝을 세고, 새 청크는 t_{k+1} 이후에 도착합니다(식 7). L = 1이면 보상이 배치의 구성이 아니라 크기에만 의존해 로봇 선택 정보가 사라집니다. 실제 알고리즘은 1초 창이라 식과 다릅니다(`03` V10, `04` D2).

### 3.3 Armory (§3.3, 부록 A.9)

- 푸시 기반: 로봇이 매 제어 스텝 행동 a_t를 실행하기 전에 관측 o_t를 보냅니다.
- 프로세스 분리: 프런트엔드(WebSocket), 스케줄러(거울과 배치 결정), 엔진(GPU 순전파)이 공유 메모리로 통신. 엔진은 시작 시 배치별 d_infer를 측정하고, d_obs와 d_action은 로봇별로 계속 추정합니다(지수이동평균, 부록 A.6).
- 엔진은 같은 요청이 다시 오거나 H_min 개를 실행하지 않은 로봇의 요청을 배치에서 뺍니다(부록 A.9). π0.5는 공식 JAX 구현을 씁니다.
- 스케줄러는 work-conserving: GPU가 놀고 쓸 만한 요청이 있으면 바로 보냅니다.

## 4. 실험 (§4, 부록 A)

### 4.1 설정

| 항목 | 시뮬레이션 | 실로봇 |
|---|---|---|
| 서버 | L40S 1장, 네트워크 왕복 5–10 ms, 서버와 클라이언트 노드 분리 | 같음 |
| 모델 | π0.5-LIBERO (H = 10, f_c = 20) | π0.5 미세조정 (H = 20, f_c = 30) |
| 로봇/환경 | LIBERO-10에서 무작위 2개 과제, 로봇 N = 2..10, 5분 창, 에피소드 타임아웃 30초 | AgileX PiPER 10대, RealSense D435i 2대씩 |
| 빠른/느린 | H_max = 6 / 10, H_min = 1 | H_max = 10 / 20, H_min = 5 |
| 과제 | LIBERO-10 | 벽돌 분류(정적), 턴테이블 벽돌 집기(동적) |
| 배치 상한 b | 3 | all-fast 3, 이질 5 |
| 시드 | 3 | 3 (각 60초 창) |
| 구성 | all-fast, one-fast, half-fast (표 4) | 같음 (표 5, 그림 4) |
| 가중치 | LA w = 1, 3, 5 (빠른 로봇만 가중) | LA w = 1, 5 |

지표: **기아율**(제어 스텝 중 행동이 없는 비율)과 **처리량**(시뮬: 분당 성공 수, 실로봇: 분당 분류한 레고 개수)(§4.1).

### 4.2 결과 요약

1. **지평과 기아의 과제 의존성(그림 3).** 동적 과제는 최소 실행 지평이 커지면 처리량이 급감하고, 정적 과제는 완만합니다. 기아율에도 같은 차이가 있습니다. 그림 3은 오차 막대 없이 곡선만 있습니다.
2. **동질 구성(all-fast)에서는 단순 스케줄러도 비슷합니다.** 시뮬 표 4와 실로봇 표 5 모두 RR, EDF, LA가 비슷합니다(§4.2, 부록 A.7).
3. **이질 구성에서 가중치가 처리량 배분을 조절합니다.** 시뮬 one-fast에서는 LA@5가 빠른 계층의 처리량을 유지하고 기아를 낮춥니다. half-fast에서는 LA@3이 가장 쓸 만한 동작점이고 LA@5는 느린 계층을 크게 희생합니다(그림 6, §4.2).
4. **실로봇(그림 4, 표 5).** one-fast에서 LA@5가 총 처리량 83 → 99(약 +18%), 빠른 계층 4배(대 RR)·2배(대 EDF). half-fast에서는 총량은 같고(63) 빠른 계층 몫이 늘어납니다.
5. **배치 크기(부록 A.4, 그림 7).** EDF·RR은 상한까지 채우는 경향(평균 4.6–4.7)이고 LA는 작은 배치(평균 3.3, 중앙값 3)를 고릅니다. 상한을 키울수록 EDF·RR의 기아율이 오릅니다.
6. **L 절제(표 3).** L = 2, 3이 L = 1보다 평균 기아를 "약간" 늘립니다.
7. **네트워크(그림 8).** 중앙값 지연 25–500 ms, 지터 σ(로그정규)를 훑어 50–100 ms까지는 완만히 열화하고, 지터에는 거의 평평하다고 보고합니다.
8. **GPU와 모델(표 1, 2).** L40S 대비 H100은 배치 1–5에서 1.7–2.4배 빠르고, GR00T N1.7은 π0.5보다 배치당 증가폭이 작습니다(메모리 바운드 쪽).

### 4.3 반직관 사례의 설명 (부록 A.8)

실로봇 all-fast에서 LA가 EDF보다 처리량이 7% 높은데 기아율은 5.71 %p 높습니다. 저자는 (1) 표본이 작고 잡음이 크며, (2) 단순 비동기(naive async)가 중간에서 시작할 때 생기는 떨림을 LA가 첫 인덱스(0)에서 시작하게 만들어 줄인다는 가설을 듭니다(그림 10). 가설은 검증하지 않았습니다.

## 5. 한계 (§7)와 우리가 본 한계

저자 서술: 단일 GPU 단순 추론 모델만 가정했고, continuous batching, PagedAttention, 분산 추론과의 공동 설계는 미래 과제(§7).

우리가 본 한계:
- 실로봇 비교가 설정당 3시드·60초 창이고, 오차 막대의 의미(SD, SEM, CI)를 그림 4 캡션이 밝히지 않습니다(`03` V4).
- 총 처리량 이득(+18%)은 실로봇 one-fast 한 칸에서만 나오고, 시뮬(표 4)은 총 처리량 이득이 없습니다(`03` V5).
- 요약에서 "처리량을 올린다"고 하는데 부록 A.7은 "핵심 기여는 총 처리량이 아니라 계층 간 재분배"라고 적습니다(`03` V5, V11).
- 과제 성공(LIBERO)과 실로봇 "처리량"은 정책 품질이 아니라 시스템 수준 성과를 섞어 측정합니다.
- 그림 1의 요약 막대는 y축이 75에서 시작하고 가중 LA(LA@5)를 "LA"로만 표기합니다(`03` V9).
- 서버 지연 표(표 1)가 시뮬(H = 10)과 실로봇(H = 20) 중 어느 설정의 것인지 적혀 있지 않습니다.
- 가중치가 하나의 운영 노브라고 하나, 값 선택(1, 3, 5)에 대한 지침이 없고 half-fast에서는 N에 따라 최적 값이 바뀝니다(표 4).

## 7. 이 논문이 새로 한 것

(저자 서술) ① 다중 로봇 서빙을 닫힌 루프 스케줄링 문제로 정식화(MDP), ② 서버 쪽 로봇 상태 거울, ③ 이질 로봇에 대한 가중 Lookahead, ④ 시뮬+실로봇 10대 평가. (우리 판단) ②가 핵심 기여이고 ①의 수식(식 10, 13)은 실제 알고리즘(1초 창, 후보 청크 보상)과 어긋납니다. ③의 이득은 대부분 재분배이고 총 처리량 개선은 실로봇 한 칸입니다.
