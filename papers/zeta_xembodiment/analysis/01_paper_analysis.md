## 1. 문제와 기여

로봇 하드웨어가 계속 바뀌므로 새 로봇에서 과제 시연 없이 쓰는 **제로샷 교차 구현체(embodiment) 전이**가 중요하지만, (1) "제로샷"이 두 가지 다른 프로토콜을 가리키고, (2) 평가가 과제, 환경, 카메라, 데이터 양과 구현체 변화를 뒤섞는다는 것이 저자들의 문제 제기입니다(§1, 쪽 2).

기여 네 가지(§1, 쪽 3):
1. **프로토콜 구분.** *strict zero-shot*(목표 구현체가 모든 학습 데이터에 없음, e_t ∉ E_pre)과 *pretrain-exposed zero-shot*(사전학습에는 있으나 후학습에는 없음)을 분리해 따로 보고하자는 제안(§3, 부록 A 표 6).
2. **통제된 벤치마크.** 목표 구현체 14종(시뮬 7 + 실세계 7)을 외형만(APP), 그리퍼만(GRP), 팔만(ARM), 전체(FULL) 변화로 묶습니다(§3, §4.4).
3. **요인 분해 연구.** 상태·행동 표현(RQ1), 소스 구현체 다양성(RQ2), 보조 공동학습(RQ3), 목표 구현체 노출(RQ4).
4. **실용 지침.** 국소 EEF 표현, 소스 다양성의 통제 평가, 보조 공동학습, 노출 여부 명시.

범위 한정: 고정형 탁상 조작, 두 손가락 그리퍼, 짧은 과제(§1, §6).

## 2. 설계

### 2.1 형식화 (§3, 부록 A, M)

- 구현체 집합 E, 과제 집합 T, 시연 D(e, t). 두 단계 학습: 사전학습 D_pre = D(E_pre, T_pre), 후학습 D_post = D({e_s}, T_post) (소스 구현체 하나), 평가는 e_t ≠ e_s에서 같은 T_post. **T_pre ∩ T_post = ∅**(표 6).
- strict: e_t ∉ E_pre. pretrain-exposed: e_t ∈ E_pre이나 D({e_t}, T_post)는 쓰지 않음.
- 정책 π_θ : (o_<t, ℓ) → a_{t:t+K} (부록 M).

### 2.2 상태·행동 표현 (§4.1, 표 1, 부록 L)

b는 로봇 베이스 프레임, e_t는 시각 t의 그리퍼 프레임, V(T) = [p, Euler(R)](오일러 순서는 논문에 명시 없음).

| | 정의 |
|---|---|
| World-Delta 행동 | {V(T_{b,e_{t'+1}}) − V(T_{b,e_{t'}})} (베이스 프레임 좌표의 차) |
| EEF-Delta 행동 | {V(T_{b,e_{t'}}^{-1} T_{b,e_{t'+1}}) = V(T_{e_{t'},e_{t'+1}})} (현재 그리퍼 프레임의 상대 변환) |
| Abs. EEF 상태 | {V(T_{b,e_{t−i}})}_{i=0}^{h−1} |
| EEF-Delta 상태 | {V(T_{b,e_t}^{-1} T_{b,e_{t−i}})}_{i=0}^{h−1} = {V(T_{e_t,e_{t−i}})} |

- 2 × 2 = 네 조합. 상태 이력은 4스텝(부록 K), 그리퍼 스칼라가 덧붙고, 행동은 12스텝 청크의 7차원(Δp 3 + Δφ 3 + 그리퍼 {−1, 0, +1}, 부록 L).
- 논문은 "state-free 정책은 h = 0인 퇴화 EEF-Delta 상태"라 주장합니다(§4.1). 그러나 합 기호는 i = 0 .. h−1이므로 h = 0이면 이력이 **빈 집합**이고, 항등 변환 T_{e_t,e_t} = I가 들어 있다는 설명은 h = 1일 때의 얘기입니다(`03` K4).
- 핵심 직관: EEF-Delta 표현은 베이스 프레임 정의에 의존하지 않고 손목 카메라의 국소 움직임 의미와 맞습니다(§4.1). 이 불변성은 `analysis/toy_frame_invariance.py`로 확인했습니다(`03` V11).

### 2.3 데이터 구성 (§4.2, 부록 F, H.5)

- **사전학습 640K 궤적**(고정 총량)의 pick-and-place를 시뮬레이터에서 생성. 소스 구현체 **512개를 Franka 계열에서 절차적으로 생성**(팔 링크 6개를 0.7–1.3배 축척, 그리퍼 손가락 길이·폭·두께, 접촉 플랭크, 6–8색 저채도 팔레트, 부록 F, 그림 2, 9).
- 목표 7종(상용 로봇)은 소스 풀에서 **제외**된 외부 구현체입니다.
- 도메인 랜덤화: 재질 1,000종 이상, Objaverse 필터 물체 10,000개 이상, 조명, 책상 높이, 3인칭 카메라 ±150° 회전·피치 15–45°·거리 0.8–1.4 m, 손목 카메라 0.1 m 입방, 질량·마찰(부록 F).
- **후학습**: 소스(시뮬은 Franka, 실세계는 Franka-Robotiq)의 하위 과제 데이터만. 시뮬 과제당 40K 궤적(3과제), 실세계 과제당 50 시연(2과제, 부록 H.5). 후학습 데이터는 "장면, 물체 조합, 조명, 카메라 배치를 하나로 고정"해 소규모 실세계 수집을 흉내냅니다(부록 F 끝).
- 평가 장면은 후학습과 **같은 물체 인스턴스, 배경, 조명, 책상 배치, 초기 자세 영역(30 × 40 cm)**(§5.1, 부록 H.3). 카메라는 정준 자세에서 이미지 평면의 그리퍼 분포가 후학습과 비슷하도록 정렬합니다(부록 H.2).

### 2.4 보조 공동학습 (§4.3, 부록 I, 표 25)

- 언어-행동(LAP): 델타 행동을 "move forward 3 cm; close gripper" 같은 문장으로 예측. EEF 프레임 변형과 베이스·EEF 혼합 변형.
- 하위 목표(subgoal): 다음 조작 관련 경유점을 현재 EEF 프레임의 [x, y, z, roll, pitch, yaw] 십진수 문자열로 예측.
- 과제 조건 BBox: 뷰마다 목표 물체 상자를 [−1, 1] 정규화, 256칸으로 양자화한 토큰으로 예측.
- 모방 예시 0.75 : 보조 질의 0.25 비율로 샘플링, 보조 응답은 다음 토큰 교차엔트로피(모방 손실 대비 가중치 0.25), 모방은 flow matching. **사전학습과 후학습 둘 다에서** 켭니다(§4.3, 부록 I, K).

### 2.5 모델과 평가 (§5.1, 부록 H, K)

- 백본: π0.5를 따르는 Mixture-of-Transformers(VLM 스트림과 분리된 행동 전문가, 층별 어텐션 결합). 입력 224 × 224 두 뷰(손목, 3인칭), 12스텝 행동 청크, 99분위수 정규화.
- 사전학습: 배치 320, **H800 16장, 120K 스텝**. 후학습: 배치 160, **H800 8장, 100K 스텝**(부록 K). 추론 1회 168 ms, 6,168 MiB(RTX 4090, 부록 L).
- 점수: 롤아웃마다 s ∈ {0, 0.5, 1}(완수 1, 과제 관련 물체 접촉 0.5, 그 외 0, 부록 H.4)의 100배를 평균한 "과제 진행도".
- **집계(부록 H.4):** 실행마다 로봇별로 과제 평균 → 범주 안 로봇 평균 → 네 범주 산술평균. 소스 열(e_s)은 평균에서 빠집니다. ±는 세 실행 집계값의 표준편차.
- 규모: 시뮬 모델당 3과제 × 7목표 × 100롤아웃 × 3실행 = 6,300, 실세계 2과제 × 7목표 × 10회 = 140(§5.1).

### 2.6 구현체 목록 (§4.4, 부록 G, 그림 3)

| 범주 | 시뮬(소스 Franka) | 실세계(소스 Franka + Robotiq) |
|---|---|---|
| APP | Franka+로고, Franka+초록 손가락 | Franka+Robotiq(CoRL 로고) |
| GRP | Franka+UMI 그리퍼 | Franka+UMI |
| ARM | UR5e+Franka 손, GoogleRobot+Franka 손 | UR5e+Robotiq |
| FULL | UR5e+UMI, GoogleRobot | 휴머노이드(오른팔), UR+UMI, 휴머노이드+UMI, Piper(Unitree B2 4족 위) |

시뮬 과제: 소시지 서빙, 그릇 쌓기, 큐브 쌓기. 실세계 과제: 에어프라이어 열기, 화분에 물 주기(그림 3). 모바일 베이스 상태와 명령은 모델 입출력에서 제외합니다(부록 G). 시뮬은 MuJoCo 물리와 IsaacSim 렌더링(부록 H.1).

주의: 실세계 범주별 로봇 수가 다릅니다. APP, GRP, ARM은 각 **1대**, FULL이 4대이고, 범주 평균은 단순 평균이라 1대짜리 범주가 FULL의 로봇 한 대보다 4배 무겁게 반영됩니다(`03` V7).

## 3. 결과 (논문 보고 수치)

### 3.1 RQ1 상태·행동 표현 (§5.2, 표 2 시뮬, 표 3 실세계)

|---|---|---|---|---|---|---|---|---|
| Abs. EEF | World-Delta | 87.7 | 86.3 | 82.6 | 38.5 | 33.9 | 60.3 ± 1.1 | 56.0 |
| Abs. EEF | EEF-Delta | 92.6 | 91.8 | 88.2 | 39.9 | 38.6 | 64.6 ± 0.4 | 61.6 |
| EEF-Delta | World-Delta | 87.8 | 88.0 | 77.2 | 69.8 | 58.4 | 73.4 ± 0.7 | 60.8 |

- 본문 결론: EEF-Delta 상태가 ARM, FULL을 크게 올리고(38.5–39.9 → 69.8–74.3, 33.9–38.6 → 58.4–60.4), EEF-Delta 행동이 평균을 올립니다(60.3 → 64.6).
- "대형 구현체 간극에는 EEF-Delta 상태+행동을, 외형·그리퍼 변화뿐이면 Abs. EEF 상태 + EEF-Delta 행동도 경쟁력 있다"(§5.6).

### 3.2 RQ2 소스 구현체 다양성 (§5.3, 그림 4, 5, 부록 표 11–13, 22, 23)

- **고정 총량(640K) 비교**: 소스 1, 8, 512개. 구현체당 궤적이 640K → 1,250으로 줄어듭니다(640,000 / 512 = 1,250). 시뮬은 512가 1보다 평균 약 18%p 높고 GRP, ARM, FULL에서 이득이 큼. 실세계는 **8 소스에서 ARM과 FULL이 1 소스보다 낮아지는 비단조**.
- **고정 구현체당 예산 비교**(그림 5): 32, 128, 512 소스, 총량이 소스 수에 비례. 시뮬 평균이 증가, 실세계도 같은 경향이라고 서술. **수치는 그림에만 있고 표가 없습니다.**
- 주의 시각화(그림 4c), UMAP(부록 E, 그림 7: 3,600 프레임, 궤적 1,200개, 목표 두 종)은 "정성적, 예비 증거"입니다.

### 3.4 RQ4 목표 구현체 노출 (§5.5, 그림 6, 표 5, 부록 J, 표 17–19)
