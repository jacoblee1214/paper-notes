## 1. 한 줄 요약

카메라 한 대(또는 여러 대)의 RGB(-D) 영상에서 MediaPipe와 신경망으로 손 자세를 추정하고, 여러 카메라 결과를 상대 회전 보정과 신뢰도로 융합한 뒤, 손가락 키포인트 벡터를 로봇 손 관절로 최적화하여 옮기고, 팔의 충돌 회피 궤적은 CuRobo로 만드는 **모듈형 원격조작 서버**입니다. 임의 팔·손, 임의 시뮬레이터(IsaacGym, SAPIEN)와 실로봇, 웹 브라우저 뷰어를 같은 틀에서 씁니다.

## 2. 방법

### 2.1 설계 목표와 시스템 구조 (§III, 그림 2, 그림 3, 표 I)

- 여섯 가지 기능 주장: 임의 팔-손(Any arm-hand), 임의 현실(Any reality: 시뮬과 실로봇), 원격 조작(브라우저 뷰어), 임의 카메라 구성(RGB 또는 RGB-D, 1대 또는 여러 대, **외부 보정 불필요**), 임의 조작자-로봇 짝(협업), 컨테이너 배포(docker, §III-A.6).
- 구조 (그림 3): 카메라 드라이버 → 텔레오퍼레이션 서버(손 검출, 검출 융합, 손 리타게팅, 동작 생성) → 관절 명령 → 클라이언트 → 시뮬레이터 또는 실로봇. 웹 뷰어가 시뮬 상태를 브라우저로 보냅니다.
- 표 I은 9개 시스템과 비교합니다. 열은 보정 불필요, 접촉, 깊이, 여러 팔, 여러 손, 실제/시뮬 영역, 충돌 회피, 원격 조작, 협업입니다. 주장: AnyTeleop만 여러 팔과 협업을 모두 지원하고 여러 손을 지원하는 두 시스템 중 하나입니다. 표 I의 셀은 원자료 대조를 하지 않았습니다(03 C5).

### 2.2 손 자세 검출 (§IV-A)

- 손가락 키포인트: MediaPipe Hands(21개 3D 키포인트, 손목 좌표계; 2D는 영상 좌표계). "CPU에서 실시간"이라고 씁니다.
- 손목 자세 (RGB-D): 키포인트 픽셀의 깊이로 카메라 좌표계 3D 점을 만들고 PnP로 손목 6D 자세를 구합니다.
- 손목 자세 (RGB만): 손의 회전은 키포인트 배치에서 해석적으로 구합니다. 위치는 FrankMocap 방식의 신경망이 예측하는 약한 원근 배율로 근사합니다. 논문은 이 위치 오차가 깊이 카메라보다 크다고 씁니다(정량 값 없음).

### 2.3 여러 카메라 융합 (§IV-B)

- 자동 보정: 첫 N = 50 프레임의 손 검출로 카메라 사이 상대 회전 SO(3)를 구합니다. 절대 위치는 RGB만일 때 부정확하지만 프레임 사이 상대 운동은 안정적이라고 씁니다.
- 신뢰도: SMPL-X 손 형상 파라미터([40], 방식은 [43]을 따름)를 쓰는데, 첫 N 프레임 평균을 기준으로 현재 예측과의 차이를 신뢰도 오차로 씁니다. 차이가 가장 작은 카메라의 상대 운동을 전달합니다.
- 보정 전제: 조작자가 첫 50 프레임에 손가락을 펼쳐야 합니다.

### 2.4 손 리타게팅 (§IV-C, 식 (1))

논문 식 (1):

min_{q_t} Σ_{i=0}^{N} ‖α v_t^i − f_i(q_t)‖² + β ‖q_t − q_{t−1}‖²,  s.t. q_l ≤ q_t ≤ q_u

- v_t^i: 사람 손 키포인트 벡터, f_i(q_t): 로봇 손 전방 기구학의 같은 벡터, α: 손 크기 배율, β: 시간 매끄러움 가중치, q_l, q_u: 관절 한계.
- 매핑은 사람 키포인트와 로봇 손 링크의 대응을 **수동으로** 지정해야 합니다(다른 형태, 예: Dclaw). 로봇 손만 고려합니다(팔은 다루지 않음).
- α와 β의 **값은 논문에 없습니다**(§IV-C). 기본값을 가정할 수 없습니다. 이 점은 04 D2–D3에서 공식 코드와 비교합니다.

### 2.5 팔 동작 생성 (§IV-D)

- CuRobo(GPU 가속 충돌 회피 동작 생성, [56])를 씁니다. 손목 목표 자세는 25 Hz로 들어오고, 관절 공간 궤적은 120 Hz로 만듭니다. 임피던스 제어기가 이 궤적을 따릅니다.
- 이전 연구 [16]은 RMP(리만 운동 정책, [7])로 팔을 움직였습니다. 논문은 RMP가 목표 자세로 향하는 가속도만 정해 자연스러운 궤적을 보장하지 않는다고 보고 CuRobo를 택합니다.

### 2.6 웹 뷰어 (§V)

- meshcat을 기반으로 Three.js로 그립니다. 시뮬 상태를 매 시뮬 스텝 뒤 브라우저로 보내고, 여러 브라우저 창으로 여러 시점을 볼 수 있습니다(부록 C, 그림 8, 9).
- 협업과 원격 조작의 근거이지만 지연 시간과 대역폭은 측정하지 않았습니다.

## 3. 실험

### 3.1 프로파일링 (§VI-A, 표 II)

- 데스크톱(RTX 3090, i9-10980XE)과 노트북(RTX 2070, i7-8750)에서 모듈별 시간(ms, 평균 ± SD). 손 검출 RGB 26 ± 5 / 34 ± 5, RGB-D 27 ± 5 / 35 ± 5, 융합 1 ± 0 / 1 ± 0, 리타게팅 9 ± 7 / 10 ± 9, 동작 생성 8 ± 3 / 11 ± 5.
- 목표는 손 검출 25 Hz, 동작 생성 120 Hz입니다. 논문은 "두 기기 모두 25 Hz를 만족", "120 Hz는 같은 기기에서 모두 돌리면 어렵다", "제어 모듈은 다른 기기에서 돌릴 수 있다"고 씁니다.

### 3.2 실로봇 (§VI-B, 표 IV, 그림 4)

- 로봇: XArm6 팔 + Allegro 손, 카메라 RealSense 한 대. 과제 10개는 Telekinesis [54]의 10개 과제를 같은 또는 비슷한 물체로 재현.
- 방법: 조작자 한 명이 과제마다 10회 시도. 기준선 [54]의 성공률은 그 논문에서 **그대로 옮겼습니다**(시도 수 미상).
- 결과: AnyTeleop이 10개 중 8개에서 높고 2개에서 같습니다(표 IV). 가장 큰 차이는 Two Cup Stacking 0.7 대 0.3, Cup Stack 0.9 대 0.6, Open Drawer and Pickup 0.9 대 0.6입니다. 논문은 얇은 벽 물체(컵)에서 우위가 나온다고 해석하고, 손가락 정밀 파지는 신경망 리타게팅이 약하다고 씁니다.

### 3.3 시뮬레이션 모방학습 (§VII-A, 표 III)

- 환경: SAPIEN. 과제 3개(Relocate, Flip Mug, Open Door), 각각 떠 있는 손(Floating-Hand)과 팔-손(Arm-Hand) 두 변형.
- 데이터: 과제당 시연 50개. 기준선 [43]의 시연은 원저자가 낸 것을 그대로 씁니다. 기준선 시스템은 떠 있는 손만 다루므로, 기준선의 팔-손 시연은 떠 있는 손 시연을 바꾼 "시연 변환 파이프라인"으로 만듭니다. AnyTeleop은 팔-손 시연을 직접 모은 뒤 떠 있는 손 시연으로 바꿉니다. 논문은 이 차이를 시연 품질의 이점으로 설명합니다(§VII-A).
- 학습: DAPG [46], 시드 3개, 정책당 100회 평가. 평균 ± SD는 시드 3개에서 나옵니다. 비교는 RL(시연 없음, [44]의 밀집 보상) 및 기준선 [43]과 함께 합니다.
- 결과: 6개 조건 중 AnyTeleop 평균이 기준선보다 5개에서 높고, Floating Flip Mug만 낮습니다(47.3 대 51.3). RL보다는 6개 모두 높습니다.

### 3.4 협업 (§VII-B, 그림 5, 그림 6)

- 두 조작자가 각자 다른 장소에서 로봇 한 대씩을 조작하는 손-손 전달(handover) 시연입니다. **정량 결과는 없습니다.** 협업은 설계 시연만 있습니다.

### 3.5 카메라 구성 (부록 A, 표 V)

- 과제 "Play Piano", 조작자 10회, 완료 시간과 오타율(잘못 누른 키 / 전체 키). Single RGB 109 s, 28.1 %; Single RGB-D 87 s, 21.8 %; Two RGB-D 74 s, 12.5 %.
- 표준편차와 시도별 값은 없습니다.

### 3.6 실패 모드 (§VIII)

- (i) 빠른 손 운동에서 추적 손실 → 일시 정지와 재검출(우회책: 조작자가 천천히 움직이기). (ii) 손이 자기 가림 상태일 때 부정확한 자세(우회책: 카메라를 여러 대 쓰기). 둘 다 질적 서술이며 빈도 측정은 없습니다.

## 4. 핵심 주장 목록 (본문에서 확인할 것)

1. 실로봇에서 기존 시스템보다 10개 중 8개 과제에서 높은 성공률 (표 IV).
2. 시뮬 모방학습에서 기존 시스템보다 6개 중 5개 조건에서 좋은 정책 (표 III).
3. 임의 팔-손, 임의 현실, 원격 조작, 임의 카메라 구성, 협업, 컨테이너 배포 (§III-A).
4. 카메라 여러 대와 깊이 정보가 완료 시간과 오타율을 낮춤 (표 V).
5. 구성 요소는 25 Hz와 120 Hz 목표를 만족한다 (표 II).

03에서 각각 재계산과 판정을 합니다(C1–C12).

## 5. 주장과 근거의 간격 (요약)

- 실로봇과 시뮬 비교는 시도 수가 작습니다(과제당 10회, 시드 3). 통계 검정을 하지 않았습니다. 03 §1.
- 기준선 값을 옮겨 왔고 시도 수와 조건이 달라 직접 비교가 어렵습니다(표 IV). 시뮬 비교도 시연 생성 방식이 달라 "팔-손 변형에서 기준선 시연 변환" 차이가 섞입니다.
- "더 매끄럽다", "충돌이 없다", "자연스럽다", "지연이 낮다"는 측정하지 않았습니다. 궤적 매끄러움, 충돌 빈도, 지연 시간의 수치가 없습니다.
- 협업은 정성적 시연만 있습니다.
- 공개된 코드에는 검출, 융합, 동작 생성, 클라이언트가 없습니다(04 §3). 실제 시스템 재현 근거는 논문 서술뿐입니다.
- 공식 저장소가 없었다면 "구현할 수 있는지"는 논문 서술로만 판단해야 했습니다. 다행히 리타게팅과 뷰어 코드가 있어 04에서 대조합니다.
