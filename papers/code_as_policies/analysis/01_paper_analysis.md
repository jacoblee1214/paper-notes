## 1. 문제와 주장

로봇에게 언어로 지시하려면 보통 (a) 언어를 고정된 기술 집합에 연결하는 계획기, (b) 언어 조건부 정책, (c) 데이터로 학습한 end-to-end 모델을 씁니다. 저자들은 이 셋이 각각 "기술 집합을 미리 정해야 하거나", "데이터가 많이 필요하거나", "새 종류의 피드백(예: 물체가 보이면 멈춤)과 수치 표현(예: '조금', '더 빠르게')을 다루기 어렵다"는 문제가 있다고 봅니다.

이 논문의 주장은 **code-writing LLM이 로봇 정책 코드를 직접 쓸 수 있다**는 것입니다. 정책 코드는 (i) 지각 출력에 따라 분기하고 반복하며, (ii) 제어 API의 매개변수를 정하고, (iii) 필요한 함수를 재귀적으로 정의할 수 있습니다. 사용자의 지시는 주석으로 들어가고, 예시 몇 쌍으로 few-shot 프롬프트를 만들면 LLM이 새 지시에 맞는 코드를 씁니다. 이를 **Code as Policies(CaP)** 또는 **언어 모델 프로그램(LMP)**이라고 부릅니다.

논문이 내세우는 기여는 네 가지입니다(§I, 기여 목록 (i)–(iv)).

1. 로봇 정책을 LLM 코드 생성으로 보는 정식화.
2. 계층 코드 생성(정의되지 않은 함수를 재귀적으로 생성) 방법. HumanEval에서 P@1 39.8%를 보고합니다.
3. 로봇 관련 코드 생성 벤치마크(RoboCodeGen, 37문제).
4. 일반화 유형별 분석과 모델 크기에 따른 "스케일링" 관찰.

실로봇과 시뮬레이션의 적용 예시(§IV-B–E)는 기여 목록에 있지만, 정량 결과는 시뮬레이션에만 있습니다.

## 2. 방법

### 2.1 LMP의 구성 (§III)

- **힌트(hints):** import 문과 타입 힌트로 쓸 수 있는 API를 알려 줍니다. 예: `from utils import get_obj_names, put_first_on_second`.
- **예제(examples):** "지시 주석 + 정답 코드" 쌍입니다. 산술, 라이브러리 호출, 제어 흐름을 보여 줍니다.
- **세션:** 이전 지시와 응답을 프롬프트에 덧붙여 "방금 한 것을 취소해" 같은 참조를 처리합니다.
- **실행:** 생성 코드를 `exec(code, globals, locals)`로 실행합니다. `globals`에는 API가 들어 있고, 실행 전에 import, `__`, exec·eval을 막습니다(D1, `04`).

### 2.2 계층 함수 생성 (§III, §IV-A)

생성된 코드의 AST를 보고 현재 범위에 없는 함수 호출을 찾아, 그 함수를 정의하는 LMP를 다시 호출합니다. 깊이 우선으로 반복합니다. 예: `stack_objs_in_order`가 `put_first_on_second`를 쓰고, 이 함수가 아직 없으면 정의를 만듭니다. 저자들은 이를 "chain of thought를 함수형으로 쓴 것"이라고 봅니다.

이 방법은 프롬프트 엔지니어링의 한 형태입니다. 생성 깊이, 재시도 횟수, 실패 시 행동은 논문에 상세하지 않습니다(`04` D5).

### 2.3 LMP의 역할 (§III-D)

LMP는 지각 출력(상태)을 프로그램으로 다루고, 그 결과로 제어 API의 인자(행동)를 정합니다. 지각과 제어는 API로 고정되어 있고, LLM은 그 사이의 논리만 씁니다. 저자들은 이 분업이 "데이터 수집 없이 일반화를 얻는다"는 이점을 준다고 말합니다.

### 3.1 코드 생성 벤치마크 (표 I, II)

- **RoboCodeGen(표 I):** 37문제. 공간 추론(가장 가까운 점), 기하(상자 포함), 제어(PD 제어)를 다룹니다. 함수 헤더에는 docstring과 타입 힌트가 없습니다. 모델은 GPT-3 6.7B(text), 175B(InstructGPT, text-davinci-002), Codex cushman(code-cushman-001), Codex davinci(code-davinci-002)입니다.
- **HumanEval(표 II):** 계층 생성 P@1 39.8%(평면 34.9%), greedy 53.0%(평면 45.7%). 부록 D(표 V)에서 code-davinci-001(36.0), PaLM Coder(36.0)와 비교합니다.

표 I의 결과는 "계층 생성이 네 모델 모두에서 낫다"입니다. 다만 6.7B와 cushman의 차이는 1–2문제입니다. 자세한 검증은 `03` §1, `04` D2–D4에 있습니다.

### 3.2 시뮬레이션 테이블탑 (표 III, VI)

- **과제:** 블록 10개와 그릇 10개. 장기 과제 8개(Socratic Models와 Inner Monologue가 쓴 시뮬 환경의 과제, 논문 [16], [18])와 공간 기하 과제 6개. 과제마다 속성(색, 방향, 거리)을 샘플링합니다.
- **분할:** 지시문과 속성을 본 것(SI, SA)과 새 것(UI, UA)으로 나눕니다. 장기 과제는 지시 1–5(본 것)와 1–3(새 것), 공간 기하는 6–8(본 것, 본문은 "5–8"이라고 씀)과 4–6(새 것)입니다.
- **기준선:** CLIPort(언어 조건부 행동 복제, 시연 30k), CLIPort의 oracle 종료 변형, NL 계획기(LLM이 언어로 계획을 씀, 공간 기하는 N/A).
- **결과(표 III):** 본 과제·본 속성 장기: CaP 97.2, CLIPort 78.8, NL 86.4. 새 속성 장기: CaP 97.6, CLIPort 36.8, NL 88.0. 새 과제·새 속성 장기: CaP 80.0, NL 64.0, CLIPort 0.0. 공간 기하는 CLIPort(본 과제) 97.3이 CaP 89.3보다 높습니다.

### 3.3 공간 추론(표 IV)

객체 선택(28문항)과 위치 선택(23문항, 노트북 기준이며 논문 본문에는 문항 수가 없습니다)에서 바닐라 언어 프롬프트 35%, CoT 58%, LMP(코드) 98%입니다. 저자들은 "수치 계산이 필요한 곳에서 코드가 CoT를 이긴다"고 결론합니다.

## 4. 결과 요약

- **코드 생성:** 계층 생성은 RoboCodeGen과 HumanEval에서 평면 생성보다 점수가 높습니다. 효과는 강한 모델(code-davinci-002, 175B)에서 커 보이지만, 약한 모델에서는 작거나 사라집니다.
- **시뮬레이션:** 새 속성과 새 과제에서 CaP는 CLIPort보다 훨씬 높고, 언어 계획기보다 높습니다(장기 과제). 본 과제의 공간 기하에서는 CLIPort가 더 높습니다.
- **실로봇:** 그림 2의 시연들은 성공 여부와 시도 횟수가 없습니다. 정성적 증거입니다.
- **한계(§V):** 지각 API가 표현할 수 있는 것에 제한이 있고, 제어 원시 동작의 매개변수가 몇 개뿐이며, 긴 지시나 새 추상화 수준에서 실패합니다. 실행 가능성을 미리 알 수 없습니다.

## 5. 주장과 증거의 틈

1. **"계층 생성이 모든 모델에서 낫다"(§IV-A).** 표 I의 차이는 6.7B에서 1문제(1 → 2), cushman에서 1문제(20 → 21, 표 값으로는 54 → 57)입니다. 노트북의 cushman 평면 값(59.5)을 쓰면 계층 생성이 오히려 낮습니다. 6.7B 열은 구문 수정 모델을 거쳤습니다(D2). 표 I의 짝지은 검정은 불가능합니다. 정직하게 쓰면 "강한 모델에서 개선이 보인다"까지입니다(`03` §1).
2. **HumanEval 주장.** "보고된 수치가 최근 연구보다 높다"는 주장은 계층 생성(39.8)에만 성립합니다. 평면 생성(34.9)은 code-davinci-001(36.0)보다 낮습니다. 모델 버전도 다릅니다(§IV-A 각주, 002 대 001). 본문은 이를 인정했지만, v4에서 "001이 덜 강력할 것"이라는 단서는 빠졌습니다(§6).
3. **"164문제 중 6.5%"(부록 D).** 정수 개수로 되지 않으며, 44%와 56%는 25의 배수 문제 집합을 가리킵니다(`03` §1.4). 본문 숫자에 오류가 있거나 모집단을 설명하지 않았습니다.
4. **표 VI의 Total 행.** NL 계획기 Total은 장기 과제만, CaP Total은 장기와 공간 기하 전체를 평균합니다. 같은 과제로 비교하면 UA-UI는 64.0 대 80.0이고, 표의 71.0 대 64.0이 아닙니다(`03` §2.2).
5. **공간 기하 과제 선택.** NL 계획기가 공간 기하에서 N/A인 것은 과제 선택의 결과입니다. 이 과제군에서 CaP의 우위를 주장하는 근거는 CLIPort뿐입니다. 그런데 본 과제 공간 기하에서 CLIPort가 CaP보다 높습니다(97.3 대 89.3).
6. **기준선의 설계.** 표 III의 CLIPort는 oracle 종료 변형입니다. 종료 없는 변형은 장기 과제 18.4%(본 과제)입니다. 시뮬레이터 정보를 쓰는 기준선과 쓰지 않는 기준선을 함께 보고했다는 점은 좋습니다. 그러나 표 III 캡션에는 어느 쪽인지 적혀 있지 않습니다.
7. **인지는 정답입니다.** 시뮬 환경의 `get_obj_names`는 장면의 모든 객체를 돌려줍니다(`04` D8). CaP의 인지 실패는 측정되지 않습니다. 실로봇의 MDETR과 ViLD 인지는 정성적으로만 보입니다.
8. **표 III의 값 불일치.** UA-UI 공간 기하의 CLIPort 값이 표 III은 0.01, 표 VI에서 계산하면 1.33입니다(`03` §2.1).
9. **"정책 안전성"과 실행 검사.** 논문은 import, `__`, exec·eval 검사만 씁니다. 샌드박스가 아니므로 실행된 코드가 파일을 읽거나 쓸 수 있습니다. 로봇에서 쓴다면 허용 API 목록을 따로 강제해야 합니다(`04` D1).
10. **스케일링 주장.** 모델 크기 두 개씩(6.7B 대 175B, cushman 대 davinci)만 비교합니다. "스케일링 법칙"이라고 부르기에는 점이 적습니다. 두 점 사이의 차이는 크지만, 모델 계열이 다르기도 합니다(GPT-3 대 Codex).
11. **실로봇은 정성적입니다.** 그림 2의 성공 사례는 시도 횟수와 실패 사례가 없습니다. "정밀한 공간 추론을 한다"는 주장은 몇 개의 시연으로 뒷받침됩니다.

## 6. 버전 차이 (v1 대 v4)

v1(2022-09-16)과 v4(2023-05-25) 본문을 단어 단위로 비교했습니다(`03` §4). 요점은 다음과 같습니다.

- 표 I–VI의 수치는 모두 같습니다.
- 표 III 캡션: "50 episodes per task"에서 "50 trials per task"로 바뀌었습니다.
- 부록 D: v1의 "code-davinci-001은 code-davinci-002보다 성능이 낮을 것이다"라는 단서가 v4에서 빠졌습니다. v4는 "상대 개선은 일관된다"만 씁니다.
- v4에 새로 들어간 내용: 열린 과제의 평가가 어렵다는 설명(§IV), 객체 중복 인식의 한계(지각 모듈 문제로 설명), 교차 구현체 예시의 "brittle" 단서, 그림 7 캡션.
- 프롬프트 링크의 확장자가 `.py`에서 `.txt`로 바뀌었습니다(프로젝트 페이지 기준).

## 7. 재현 가능성 요약

- 표 I–VI는 재계산할 수 있습니다(`03`). 단 HumanEval의 P@N, 표 IV의 시행 수, 기준선 평가 루프는 원자료가 없습니다.
- 공식 노트북은 구성 요소의 일부를 제공합니다. 그러나 OpenAI API 모델을 쓰며, 로봇과 기준선은 없습니다(`04` §4).
