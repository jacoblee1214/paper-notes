## 1. 식 3을 다시 읽기: 카메라 갱신은 "geometry로 설명되지 않는 잔차"의 합

두 시점 BA에서 점 i의 geometry 변수 g_i(toy에서는 역깊이 ρ_i 하나)는 자기 잔차에만 들어갑니다. 그래서 식 2의 C = J_gᵀJ_g가 **블록 대각**이고, Schur 보완을 점별 합으로 쓸 수 있습니다.

```
S = B − E C⁻¹ Eᵀ = Σ_i  J_c,iᵀ ( I − J_g,i (J_g,iᵀ J_g,i)⁻¹ J_g,iᵀ ) J_c,i  =  Σ_i  J_c,iᵀ P_i⊥ J_c,i
v − E C⁻¹ w     = − Σ_i  J_c,iᵀ P_i⊥ r_i
```

P_i⊥는 "점 i의 깊이를 움직여서 설명할 수 있는 방향"을 지우는 사영입니다. 즉 **카메라 갱신은 각 점이 자기 geometry로 흡수하지 못하는 잔차 성분만 모아서** 정해지고, 그다음 역대입 Δg = C⁻¹(w − EᵀΔc)로 점마다 독립적으로 geometry를 고칩니다. 논문이 식 3에서 읽어 낸 "잔차 → 카메라(모음) → geometry(개별)"의 흐름이 이것입니다.

**toy 확인 (T1, N = 60):** 식 3으로 푼 (Δc, Δg)와 전체 정규방정식 해의 최대 차이는 1.4×10⁻¹⁴이고, C의 비대각 성분은 정확히 0입니다. 그래서 C⁻¹은 O(N)이고 S는 6×6입니다.

**BA-T와의 대응과 차이 (내 해석):**

- 식 8의 "카메라 토큰 1개 ← 잔차 토큰 N개 cross-attention"은 Σ_i의 학습판입니다. 다만 attention 가중치는 합이 1인 **가중 평균**입니다. 고전 BA에서는 S가 N에 비례해 커지고(정보가 쌓임) 그만큼 카메라 추정이 정밀해지는데, 평균은 크기가 N에 따라 자라지 않습니다. 정밀도 누적은 평균 안에서 잡음이 상쇄되는 효과로만 남습니다.
- P_i⊥(자기 geometry로 설명되는 성분 제거)에 해당하는 장치는 BA-T에 명시적으로 없습니다. 잔차 MLP(식 7)와 camera_attn의 MLP가 학습으로 이를 흡수해야 합니다.

## 2. 파라미터 산술: "38M"은 무엇을 세는가

`param_check.py`는 torch 없이 공식 코드(`406d791`)의 Linear·LayerNorm 크기를 더합니다. 전체 344.4M × 4바이트 = 1.378 GB가 HF 체크포인트 파일 크기(1.378 GB, `bat.pth`·`bat_paper.pth` 모두)와 일치하므로, 이 셈이 맞다고 볼 수 있습니다.

|---|---|
| token_transform (adaLN 조건 블록: ModLN 2개 + self-attn + MLP) | 9.45 |
| self-attention 3개 (LN + attn, **MLP 없음**) | 7.09 |
| geometry cross-attention 층 (MLP 포함) | 7.09 |

| 주변: appearance_embed 0.79 + point map 헤드 0.79 + 포즈 헤드 0.93 + 초기 토큰 | 2.50 |

- 논문의 "디코더 38M"은 **BA 층 하나만** 센 값입니다(38.40M). 헤드와 입력 투영을 넣으면 40.9M이고, 전체 모델에서 디코더 몫은 11.9%입니다.
- **부록 A대로라면 38M이 아닙니다.** 부록 A는 "self-attention 3개, 각각 MLP(확장비 4)", "잔차 MLP 확장비 4"라고 씁니다. 이대로 세면 52.6M(self-attention MLP만), 56.1M(잔차 MLP까지)입니다. 코드가 38M에 맞으므로, 부록 A가 실제 모델을 잘못 서술한 것으로 봅니다(`04` D3, D4).
- **ViSTA† 산술:** 같은 계열 DecoderBlock(768차원: self-attn + cross-attn + MLP + LN 4개)은 층당 9.45M입니다. 12층 = 113.4M으로 ViSTA의 113M과 정확히 맞으므로, 3층은 28.4M이어야 합니다. "3층으로 38M에 정확히 맞춤"(부록 B)이 성립하려면 4층(37.8M)이거나 층 밖에 약 9.8M이 더 있어야 합니다. 어느 쪽인지 논문과 코드로는 확인할 수 없습니다.
- **크기 비율:** 38/227 = 16.7%(DUSt3R, 초록 "16%"), 227/38 = 5.97배(v2 "최대 6배"), 38/605 = 6.3%(VGGT), 38/765 = 5.0%(DA3), 38/171 = 22.2%(MapAnything). "5–6%"는 MapAnything을 빼야 성립합니다.

## 3. 갱신 순서 toy (T2, T2b)

논문(§3.3, 알고리즘 1)은 Schur 순서대로 **카메라 먼저, 그다음 갱신된 카메라로 geometry**라고 씁니다. 공개 코드(`BundleAdjustmentLayer.forward`)는 **geometry 먼저(이전 카메라 토큰으로 변환), 그다음 새 geometry의 잔차로 카메라**입니다(`04` D1). 학습된 층에서 이 차이가 무엇을 뜻하는지는 직접 확인할 수 없으므로, 고전 BA에서 세 가지 갱신 방식을 비교했습니다.

**설정:** 시점 a의 광선 방향 f_i(고정)와 역깊이 ρ_i(geometry), 상대 포즈 (R, t)(카메라). 잔차는 시점 b 재투영 오차 2N개(1 px 잡음, 초점거리 500)와 단안 깊이 사전 w·(ρ_i − ρ̂_i) N개(사전 잡음 10%, w = 0.05)입니다. 깊이 사전은 스케일을 고정하고, 인코더의 단안 geometry 사전(부록 F.2) 역할을 합니다. N = 40, 시드 10개 중앙값.

- **joint:** 식 3 그대로 한 번에 풀기
- **카메라 먼저 (논문 순서):** 현재 geometry로 카메라만 풀고 → 재선형화해서 새 카메라로 geometry만 풀기
- **geometry 먼저 (코드 순서):** 현재 카메라로 geometry만 풀고 → 새 geometry로 카메라만 풀기

| 기선 / 초기 회전 오차 | 방식 | 회전 오차 중앙값(°) 반복 1 / 2 / 4 | 0.2° 도달 비율 |
|---|---|---|---|
| 0.05 / 3° | joint | 0.114 / 0.092 / 0.088 | 1.0 |
| | 카메라 먼저 | 0.133 / 0.107 / 0.087 | 1.0 |
| | geometry 먼저 | 0.587 / 0.212 / 0.115 | 1.0 |
| 0.3 / 3° | joint | 0.183 / 0.130 / 0.129 | 0.9 |
| | 카메라 먼저 | 0.600 / 0.530 / 0.422 | 0.0 |
| | geometry 먼저 | 1.383 / 0.835 / 0.590 | 0.2 |
| 0.3 / 10° | joint | 0.859 / 0.132 / 0.129 | 0.9 |
| | 카메라 먼저 | 0.859 / 0.688 / 0.554 | 0.3 (8회 안) |
| | geometry 먼저 | 3.895 / 3.165 / 2.738 | 0.0 |

(기선 0.05 / 초기 10°도 같은 경향이라 표에서 뺐습니다. 전체는 JSON에 있습니다.)

**관찰:**

1. **고정점은 같습니다 (T2b).** 200회 돌리면 카메라 먼저는 joint 해와 회전 차이 1.7×10⁻⁴° 이하, geometry 먼저도 시드 셋 중 둘은 2×10⁻⁴° 이하, 하나는 0.015°까지 다가갑니다. 순서는 해를 바꾸지 않고 **수렴 속도만** 바꿉니다.
2. **번갈아 풀기는 결합이 강할수록 느립니다.** 기선이 짧으면(0.05) 재투영이 깊이를 거의 제약하지 못해 깊이 사전이 지배하고, 카메라와 geometry가 사실상 분리되어 세 방식이 비슷합니다. 기선이 길면(0.3) E C⁻¹ Eᵀ 결합이 커져, 한쪽을 고정하고 다른 쪽을 푸는 블록 좌표 하강이 지그재그로 느려집니다. joint가 2회면 끝나는 문제를 번갈아 풀기는 8회로도 다 못 풉니다.
3. **geometry 먼저가 가장 나쁜 이유:** 첫 단계에서 틀린 카메라(초기 10°)에 맞춰 깊이가 끌려가고, 그 틀린 깊이에 맞춰 카메라를 풉니다. 카메라 먼저는 깊이 사전으로 초기화된 깊이(10% 잡음)를 믿고 카메라를 먼저 맞추므로, 첫 카메라 추정이 joint와 같습니다(반복 1 회전 0.859°로 동일).

**BA-T에 주는 함의 (내 해석, 미검증):** 부록 F.2는 카메라 초기 토큰이 "거의 항등 변환으로 디코딩된다"고 했습니다. 코드 순서에서는 첫 geometry 갱신이 이 항등 근처 카메라로 이웃 시점을 변환합니다. 고전 BA 직관으로는 불리한 순서입니다. 하지만 학습된 층은 이 순서를 전제로 학습되었고, 첫 geometry 갱신이 "카메라 정보 없이 하는 시점 간 교차 attention"으로 쓰일 수도 있습니다. 순서의 영향은 같은 데이터로 두 순서를 각각 학습해야만 알 수 있습니다. 공개 체크포인트에서 순서만 바꿔 돌리는 것은 학습 분포 밖이라 의미가 없습니다.

## 4. 왜 포즈가 geometry보다 잘 좋아지는가 (T3, 부록 F.2)

부록 F.2는 두 가지 이유를 듭니다. 잔차가 카메라 갱신에 직접 들어간다는 것, geometry는 인코더 사전 덕분에 처음부터 좋다는 것입니다. 고전 BA에서 가장 단순한 형태는 **변수당 관측 수**입니다. 카메라는 6개 변수에 2N개 잔차가 모이고, 점마다의 깊이는 1개 변수에 잔차 2개 + 사전 1개뿐입니다.

| N | 회전 오차 중앙값(°) | 상대 깊이 오차 중앙값 | 단안 사전의 오차 |
|---|---|---|---|
| 10 | 0.277 | 0.024 | 0.060 |
| 40 | 0.131 | 0.015 | 0.064 |
| 160 | 0.055 | 0.013 | 0.061 |
| 비 (N10 / N160) | **5.1배** (√16 = 4) | 1.9배 | – |

포즈 오차는 N에 따라 대략 1/√N보다 조금 빠르게 줄고, 깊이 오차는 N이 늘어도 바닥(약 1.3%)에서 멈춥니다. 깊이의 바닥은 카메라 오차가 0이 되어도 남는 "점마다 재투영 2개"의 정밀도 한계입니다. BA-T 표 2에서도 반복 1→4 동안 이동 AUC는 +0.100, Corr.는 −44%로 크게 좋아지지만 Rel.은 −5.9%, δ1.25는 +0.004뿐입니다. 고전 BA의 이 구조적 비대칭은 F.2의 설명과 같은 방향이고, 학습 모델에서도 그대로 나타난다고 볼 수 있습니다(인과는 미검증).

시점별 토큰 수는 코드에서 196개(224×224, 패치 16)로 고정이라, 해상도를 올리면 카메라 쪽 "N"이 커집니다. 해상도와 포즈 정밀도의 관계는 실험되지 않았습니다.

## 5. 효율 해부 (표 5, P5)

**연산량 추정** (`param_check.py` P5, 224×224 한 쌍, 선형층 2·파라미터·토큰 + attention 4·Nq·Nk·D, softmax·LN 제외. 측정이 아니라 추정입니다):

| 부분 | GFLOP |
|---|---|
| ViT-L 인코더 (두 시점) | 245.2 |
| BA 층 1회 | 25.3 |
| └ 조건 변환 3회(이웃 2 + 잔차 1) | 11.5 (45%) |
| └ self-attention 3개 × 두 시점 | 6.3 |
| └ geometry cross-attention × 두 시점 | 5.8 |
| └ 매칭·잔차 / 카메라 갱신 | 1.3 / 0.5 |
| 헤드·입력 투영 | 1.2 |
| **합: K = 4 / K = 8** | **347.5 / 448.7** |

- K = 4에서 인코더가 연산의 71%입니다. 표 5의 시간도 같은 그림입니다. 선형 적합으로 인코더+헤드 18.3 ms, 반복당 3.2 ms이고, k = 1에서도 21.4 ms 가운데 85%가 인코더 쪽입니다. 시간 비(18.3 : 3.2 = 5.7)가 연산 비(246 : 25 = 9.7)보다 작은 것은 작은 행렬 연산의 GPU 효율 차이로 보입니다(추정).
- BA 층 안에서는 **조건 변환(adaLN 블록)이 절반 가까이**를 씁니다. 매 반복 이웃 변환 2번과 잔차용 변환 1번을 하기 때문입니다. 층을 더 줄인다면 이 부분이 첫 후보입니다.
- **메모리:** 가중치만 fp32 1.283 GiB(1.378 GB)입니다. 표 5의 1.32가 GiB라면 활성값과 작업 공간은 약 0.04 GiB입니다. 1.32가 10⁹ 바이트 단위라면 가중치(1.378 GB)보다 작아 불가능하므로 GiB로 읽는 것이 맞습니다. 결국 메모리 비교는 전체 파라미터 비교이고, BA-T의 장점은 "디코더가 작아 전체가 작다"는 데서 옵니다.
- **이 맥에서의 추론 비용:** K = 8 기준 약 450 GFLOP/쌍입니다. CPU fp32 실효 성능을 수백 GFLOP/s로 가정하면 쌍당 약 0.5–2초, 메모리는 2 GB 미만으로 추정합니다(미측정, `04` §4).
