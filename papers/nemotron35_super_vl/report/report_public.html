핵심 요약

  1. 무엇인가: Nemotron 3 Super(텍스트, 120B-A12B)를 Ultra 3에서 1T 토큰 증류하고, Indic 계속 사전학습, 1M 문맥, 256K SWE 중간학습을 거친 뒤 사후학습에서 시각을 붙인 멀티모달 에이전트 모델이다. 교사 여러 개를 MOPD로 합치고, NVFP4 양자화와 vLLM 서빙 최적화까지 다룬 레시피·시스템 보고서다. "Lightning"은 같은 세대의 30B-A3B 텍스트 전용 소형 모델이다.
  2. 구조는 공개 config로만 확인된다: 88층(Mamba-2 40, LatentMoE 40, attention 8), expert 512개 중 top-22, KV 헤드 2개. 전체 124.45B, 토큰당 활성 12.23B로 이름과 맞다. 활성 가중치에서는 Mamba projection(35.8%)이 routed expert(39.6%)만큼 크고, attention은 2.3%뿐이다.
  3. "Ultra를 넘는다"는 부분적이다: T10 공통 27개 중 17승 10패이고, 1위는 GraphWalks 하나다. SWE-bench Pro 51.78%는 같은 OpenCode 하네스의 F8 값(41.04%)보다 10.7%p 높고, 보고서는 이 차이를 설명하지 않는다.
  4. 양자화는 중앙값보다 꼬리를 봐야 한다: 복원율 중앙값은 99.62%(36개 기준, 표 37행 전체는 99.70%, 결론에는 99.52%)지만 SciCode problem 93.6%, Tau3 Banking 94.2%가 있다. 공개 config의 SSM 상태 기본값은 float32이고, 카드의 SGLang 명령은 BF16을 쓴다. 보고서가 검증한 FP16+SR과 다르다.
  5. 메커니즘 확인: Mamba 캐시 한 페이지 = KV 4,096토큰(보고서 "약 4K"와 일치). ReplaySSM은 MTP 5에서 상태 트래픽을 약 5배 줄이지만 측정 처리량 이득은 5–6%다. 재구성 식의 곱 범위는 본문 표기(j > i+1)가 아니라 j > i다. MOPD 2단계의 proximal teacher 하한 −0.223을 toy로 확인했다.
  6. 구현 가능성: 이 맥(M4 Pro 24 GiB, CUDA 없음)에서는 Super VL을 어떤 공개 형식으로도 돌릴 수 없다(가장 작은 MLX 3비트가 39.8 GiB). 같은 세대 Lightning 30B-A3B 4비트(17.6 GiB)만 빠듯하게 가능하다. 미세조정은 LoRA도 8× H100 노드가 필요하고, 레시피는 잘 공개되어 있다.

1. Abstract (한 줄 요약과 주장)

한 줄 요약: Nemotron 3 Super(120B-A12B, 텍스트)를 출발점으로, Ultra 3 Base에서 1T 토큰 증류 → Indic 계속 사전학습 → 1M 문맥 → 256K 문맥 SWE 중간학습을 거친 뒤, 사후학습 단계에서 시각 입력을 붙이고 전문 교사 여러 개를 MOPD로 합쳐 멀티모달 에이전트 모델로 만들었습니다. 그다음 **NVFP4 양자화와 vLLM 서빙 최적화(ReplaySSM, Mamba 체크포인트 prefix caching)**까지 한 보고서에 담았습니다.

보고서가 내세우는 수치(초록, §1)는 다음과 같습니다.

  1. SWE-bench Pro **51.78%**로 Nemotron 3 Ultra(49.66%)를 넘음. 활성 파라미터는 약 4.6배 적음.
  2. Indic 계속 사전학습으로 인도 언어 벤치마크 최대 +9.82%p(T2).
  3. 사후학습 MTP boosting으로 acceptance length가 greedy에서 +10.1%, 확률적 draft sampling에서 +21.8%(T8).
  4. NVFP4 양자화 정확도 복원율 중앙값 99.62%(36개 벤치마크, §4.1). 단, 결론(§6)에는 99.52%로 적혀 있습니다(04 C8).
  5. GB200 한 장에서 사용자당 50 tok/s 이상을 유지하며 최대 4,856 tok/s/GPU(T24). 같은 조건에서 NVFP4가 BF16의 2.43배, Qwen3.5 122B-A10B의 2.34배, Qwen3.8 Flash-Next의 1.90배(F10, F11).
  6. 공개물: base·BF16·NVFP4 체크포인트, 병렬 drafter(Super용 LiLiCorr, Lightning용 DFlash·DSpark), 데이터셋, cookbook, 학습 레시피.

Lightning은 Nano 3 Base에서 시작해 Super 3 Base를 교사로 1T 증류(forward KL)하고, 장문맥 21B만 거칩니다. Indic CPT와 중간학습은 없습니다(§2.2, §2.4).

MTP의 train–inference 불일치(§2.1). 재귀 MTP를 표준 방식으로 학습하면 k번째 단계는 정답 은닉 상태로만 학습하지만, 추론에서는 앞선 MTP 단계가 만든 합성 상태를 입력으로 받습니다. Super는 학습 중 k번째 단계의 입력을 1…k−1 단계 출력에서 섞어 뽑는 hidden-state mixing으로 이 차이를 줄였습니다. 여러 단계를 실제로 펼쳐 학습하는 TTT보다 계산이 적다는 것이 근거입니다.

2.3 Indic 계속 사전학습 (§2.3, T1–T3, F2–F3)

  • 데이터: Nemotron-CC 영어 문서(4,096 토큰 미만, 분할 없이 통째로)를 Gemma-4-31B-it로 번역합니다. 번역 → 품질 점수(q ≥ 75면 채택) → 오류 수정 → 재채점의 4단계이고, 로마자 표기본도 같은 모델로 만듭니다(F2). 저자원 10개 언어는 Bodhan-MT로 번역합니다. 총 약 2.83T 토큰, 22개 언어, 34개 언어·문자 조합입니다(T1, 합계 2,825.6B 재계산 일치).
  • 비용: 번역 비용을 영어 입력 100만 토큰당 0.835 → 0.335 GPU-h로 줄였습니다(−59.9%, 2.49배).
  • 결과(T2): 5개 Indic 벤치마크가 모두 올랐습니다(+4.98 ~ +9.82%p). 다만 합성 데이터와 자연 데이터의 기여는 나누지 않았습니다(본문 명시).
  • 혼합 비율(T3): Lightning으로 200B 토큰 예산에서 Indic 10/20/30%를 비교하면 평균 63.1 / 64.6 / 65.6으로 단조 증가합니다. 공개된 Lightning에는 Indic 단계가 없습니다.

2.4 SWE 중간학습 (§2.5, T4–T5)

사전학습은 짧은 문맥이라 저장소 전체, 이슈–PR, 커밋 이력, 빌드 로그를 담기 어렵습니다. SFT는 대부분 합성 데이터이고, 너무 길면 이후 RL 이득을 줄입니다. 중간학습은 그 사이에서 자연 SWE 데이터를 256K 문맥으로 학습합니다.

2.6 MOPD: 다중 교사 on-policy 증류 (§3.6, Eq. 1–2)

학생이 직접 생성한 응답의 각 토큰에서, 그 도메인을 맡은 교사의 확률과 학생 확률의 로그 차이를 advantage로 씁니다.

Δθ ∝ E_{y ~ π̄_S(·|q)} [ Σ_t Â_t ∇θ log π_S(y_t | c_t) ]                          (Eq. 1)
Â_t = sg[ log π_T(y_t | c_t) − log π̄_S(y_t | c_t) ]                               (Eq. 2)
  • 이것은 학생 분포에서 본 reverse KL D(π_S ‖ π_T)를 토큰 단위로 최소화하는 것과 같습니다. verifier도 교사 샘플링도 필요 없고, 교사 forward 한 번이면 모든 토큰에 dense 신호가 생깁니다. 학생과 교사가 같은 곳에서는 신호가 0입니다.
  • 비동기 학습이라 한 step 늦은 응답은 π̄_S/π̄_{S−1}로 중요도 가중하고 [0.2, 5] 밖은 마스크합니다.
  • 도메인 라우팅: 각 프롬프트는 해당 교사로 가고, 교사가 없는 환경은 self-anchor(학생 시작점의 동결 복사본)로 보냅니다. self-anchor는 학생이 시작점에서 멀어질 때만 신호를 줍니다.
  • 1단계(30 step): 에이전트 35%, 추론 25%, 정렬 20%, 시각 도구 15%, self-anchor 5%. 512 프롬프트 × rollout 1, LR 2e-6.
  • 2단계(40 step): 에이전트·추론 교사는 은퇴시키고 그 환경을 self-anchor로 돌립니다. 정렬 30%, 시각 도구 20%, 시각 추론 20%, 비디오 20%, self-anchor 10%. 1,024 프롬프트, LR 3e-6. 빨리 오르고 나중에 떨어지는 도메인을 1단계에, 느리게 오르는 도메인을 2단계에 둔 배치입니다.
  • proximal teacher(2단계만): 교사를 α π_T + (1−α) π̄_S(α = 0.2)로 바꿉니다. 그러면 advantage가 아래에서 log(1−α) ≈ −0.223으로 막혀, 교사가 매우 낮게 보는 토큰도 무한히 큰 음의 신호를 받지 않습니다(03 §4에서 확인).
  • 부수 효과(부록 B.1): MOPD 전 체크포인트는 tau3-banking에서 rollout 776개 중 153개(19.7%)가 끝없이 반복하며 멈추지 못했습니다(runaway loop). MOPD 뒤에는 1개입니다. 이 차이가 NVFP4 양자화 강건성에도 이어집니다(§2.8).

2.7 MTP boosting (§3.7, T8–T9, F6)

본체를 동결하고 MTP 헤드만 두 번 학습합니다. SFT 체크포인트에서 4k step을 먼저 학습하고, 최종 체크포인트에서 25k step을 더 학습합니다. hidden-state mixing을 유지하고, loss를 CE 대신 **동결 본체를 교사로 한 증류(LK loss)**로 바꿨습니다. 데이터는 본체가 temp 1로 생성한 on-policy rollout(8K 토큰 상한)입니다.

목표: 중앙값 정확도 복원율 99% 이상, 출력 길이 증가 5% 이하. Super VL NVFP4는 Blackwell에서 W4A4, 그 밖에서는 W4A16으로 배포하고, Lightning은 어디서나 W4A16입니다.

  • PTQ(§4.2): ModelOpt로 이미지–텍스트 SFT 데이터 1,024개를 보정에 썼습니다. 블록 scale은 MSE 탐색이 Max보다 낫습니다(T13 복원율 100.06% vs 98.58%).

  • KV cache(§4.5, T18): NVFP4 KV(블록 16개당 FP8 scale, 원소당 4.5비트)는 FP8 대비 저장량이 43.75% 적습니다. 복원율은 NVFP4 KV 99.36%, FP8 KV 99.52%로 비슷했습니다. 그래도 공개 체크포인트는 소프트웨어 성숙도 때문에 FP8 KV를 기본으로 씁니다.
  • 어디가 민감한가(§4.6, 부록 B): 정확도 손실은 주로 expert 가중치에서 나옵니다. FP4로 양자화하면 멈출지 계속할지의 경계(stop-vs-continue margin)가 흔들리고, 원래 불안정하던 모델에서 runaway loop가 늘어납니다. MOPD 전 모델에서 expert를 FP8로 올리면 runaway가 28.2% → 17.9%로 줄었습니다. Mamba out_proj를 FP4로 만들면 출력이 길어지고, lm_head는 FP4에서도 정확도는 같지만 종료 판단이 흔들려 FP8 이상을 권합니다. 장문맥 구분 과제(MRCR-128k)는 attention score 해상도에 민감합니다.
  • MTP 양자화(§4.7): MTP expert를 NVFP4로 바꾸면 AL이 4.612 → 4.592입니다. MTP는 따로 양자화한 뒤 본체 체크포인트에 이어 붙였습니다(splice).

2.9 서빙 (§5)

  • 작업 부하: 20턴 에이전트 대리 부하(공유 prefix 51,200, 턴당 입력 2,048, 출력 1,024)에서 사용자당 50 tok/s 이상인 점 가운데 GPU당 처리량이 가장 높은 점을 고릅니다.
  • Mamba prefix caching(§5.3): vLLM은 attention과 Mamba의 캐시 페이지 크기를 바이트로 맞춥니다. Mamba 상태 한 페이지가 attention KV 약 4K 토큰과 같으므로(03 §2에서 정확히 4,096으로 재계산), Mamba 상태는 4K 토큰 간격으로만 저장됩니다. 투기적 디코딩과 함께 쓰면 최대 4K 토큰을 다시 계산해야 해서, 공유 prefix 경계 근처에 Mamba 체크포인트를 하나 더 두도록 바꿨습니다.
  • ReplaySSM(§5.4): 투기적 디코딩은 몇 토큰이 채택될지 모르므로 후보 위치마다 Mamba 상태를 써야 합니다. 대신 체크포인트 상태와 이후 입력(k, v, α)만 작은 버퍼에 저장하고, 필요할 때 상태를 재구성합니다. 상태 쓰기를 버퍼 길이 L에 걸쳐 분할상환하므로 상태 트래픽이 T+1에서 약 1+1/L로 줄고, 양자화 횟수도 줄어듭니다. 측정 이득은 출력 처리량 +4.7–6.4%, 사용자당 +6.4–12.5%입니다(T24). Dao lab의 동시 발견과 같은 기법입니다.
  • 분리 서빙(§5.6, T25): Vera Rubin(VR200) 11장에서 prefill 7 + decode 4로 나누면 GPU당 처리량 +10.3%, 사용자당 속도 +61%입니다. TTFT는 0.49 → 1.12 s로 늘지만 5 s 목표 안입니다.
  • 병렬 drafter(§5.7): LiLiCorr는 블록 8칸(7개 draft)을 한 번에 제안하고, 칸마다 상위 K 후보 사이의 호환성을 작은 Transformer로 점수 매겨 왼쪽부터 고릅니다(Eq. 4–5). drafter는 1.13B(헤드 37M)이고, 동시 처리량이 낮은 DGX Spark 같은 환경이 목표입니다. AL은 greedy 4.77, sampling 4.37입니다(T28).

4. Limitations

4.1 저자가 밝힌 한계

  • Indic 단계의 이득에서 합성 데이터와 자연 데이터의 기여를 나누지 않았습니다(§2.3). Lightning 혼합 비율 실험은 Super의 최적 비율을 정하지 않습니다.
  • 오염 제거 파이프라인은 저렴한 유사도 신호로 후보를 고른 뒤에만 judge가 판정하므로 재현율에 상한이 있습니다. 문제 문장만 보고, 합성 오염 실험은 대리 평가입니다(부록 C.6). 합성 변형 탐지율은 Terminal-Bench 87.5%, GPQA 79.1%입니다.
  • 양자화 원인 분석(부록 B)은 추론에 기반한 귀속이고, MRCR-128k가 유일한 구분 과제이며, 모든 구성이 FP8 KV를 쓴다는 단서를 붙였습니다.
  • 하네스에 따라 순위가 바뀌므로 하네스와 설정을 함께 보고해야 한다고 스스로 강조합니다(§3.10).

4.2 분석하며 본 한계

  1. 구조 표가 없습니다. 층 구성, expert 수, KV 헤드 같은 값은 config를 봐야 알 수 있습니다(04 D5).
  2. 같은 수치가 두 값으로 나옵니다. NVFP4 복원율이 초록·§4.1에서는 99.62%, §4.5·결론에서는 99.52%입니다. 처리량도 4,856 / 4,324 / 4,331.88로 세 값입니다(04 C1, C8).
  3. 헤드라인 SWE-bench Pro 수치는 프로토콜에 민감합니다. 같은 OpenCode 하네스인데 T10 51.78%, F8 41.04%입니다. F8의 최고값 49.45%는 T10의 Ultra 49.66%보다 낮습니다(04 C11).
  4. 불확실성 표시가 거의 없습니다. T10은 3–8회 평균이지만 표준편차나 신뢰구간이 없습니다. 벤치마크마다 1–2점 차이는 실행 간 변동(§2.5에서 "약 1점")과 구분하기 어렵습니다.
  5. MOPD와 교사 각각의 기여를 분리한 ablation이 없습니다. 비디오 교사 같은 개별 교사 점수(§3.4.1)만 있고, 최종 모델 점수가 어느 단계에서 왔는지 보여 주는 단계별 표가 없습니다.
  6. 블로그에만 있는 주장이 많습니다. "5배 처리량", "Dynamo로 8배 사용자·TTFT 85% 감소", "LiLiCorr 2.3배", "Baseten 600 TPS", "사후학습 약 3.8M 샘플"은 보고서에서 확인되지 않습니다. 3.8M은 보고서의 오염 제거 수치(20,671개 = 약 0.09%)에서 역산한 약 23M과 맞지 않습니다(04 C5, C10).
  7. 로봇·embodied 평가가 없습니다. 시각 평가는 문서·차트·OCR·비디오 QA·GUI(OSWorld) 중심입니다. 공간 추론(ERQA 등)은 SpatialClaw 하네스 효과(T7)로만 나옵니다. 로봇 VLA 백본으로 쓸 수 있는지는 이 보고서로 판단할 수 없습니다.

latent projection + 라우터 0.42 3.4% BF16
attention QKVO 0.29 2.3% FP8

해석. 전체 파라미터의 90%가 routed expert지만, 토큰 하나가 실제로 지나가는 가중치에서는 Mamba projection이 routed expert만큼 큽니다. attention은 2%에 불과합니다. NVFP4가 적용되는 부분(expert)은 활성 가중치의 54%뿐이고, 나머지 43%는 FP8입니다. 그래서 FP8 Mamba projection의 정밀도와 커널 성능이 decode 속도에 크게 작용합니다. 보고서가 Mamba out_proj의 FP4 민감도를 따로 분석한 이유(§4.6, 부록 B.4)와도 맞습니다.

1.2 배치 1 decode의 대역폭 상한

배치 1에서는 토큰마다 활성 가중치를 한 번씩 읽어야 합니다. 공개 레시피(expert 4.5비트, FP8 3종, BF16 latent)로 계산하면 토큰당 9.76 GB입니다. 메모리 대역폭이 273 GB/s인 DGX Spark(이 맥의 M4 Pro도 같은 273 GB/s)에서는 투기적 디코딩 없이 최대 약 28 tok/s입니다. 사용자당 50 tok/s 목표에 못 미칩니다. NVFP4 모델 카드가 DGX Spark에 LiLiCorr drafter(7토큰)를 "모든 경우에" 권하는 이유가 이 계산으로 설명됩니다. KV·상태 읽기를 빼고 계산했으므로 실제 값은 더 낮습니다.

  • 반대로 문맥이 2만 토큰보다 짧으면 Mamba 상태가 KV보다 큽니다. 짧은 요청이 많은 서빙에서는 상태 메모리가 동시 처리 수를 제한합니다. FP16 + stochastic rounding으로 상태를 반으로 줄인 것(T12)이 이 영역에서 의미가 있습니다.
  • prefix caching이 Mamba 상태를 4,096 토큰 간격으로만 저장하는 이유도 바이트 맞춤에서 바로 나옵니다. 투기적 디코딩과 함께 쓰면 최악의 경우 4K 토큰을 다시 계산하므로, 보고서가 경계 근처에 체크포인트를 하나 더 두는 수정을 했습니다(§5.3).

3. ReplaySSM: 닫힌 식, 트래픽, 양자화 오차 (§5.4)

3.1 닫힌 식의 지수

보고서는 decode 갱신을 S_new = α S_old + kᵀv로 적고, 체크포인트에서 재구성하는 식을 S = (∏ α_i) S_ckpt + Σ_i (∏_{j>i+1} α_j) k_iᵀ v_i로 적었습니다(47쪽). 같은 문단의 갱신식을 펼치면 i번째 입력은 그 뒤의 감쇠 α_{i+1}, …, α_n을 모두 받으므로 곱의 범위는 j > i여야 합니다. numpy로 16토큰을 펼쳐 보면 다음과 같습니다.

곱의 범위 순차 갱신 대비 상대 오차
∏_{j>i} 3.3 × 10⁻¹⁶ (정확)
∏_{j>i+1} (본문 표기) 4.7 × 10⁻³

감쇠가 1에 가까워 오차는 작지만, 본문 표기는 지수가 하나 어긋난 것으로 보입니다. 다른 색인 규약(α_i를 i번째 입력 전에 적용)을 썼을 가능성도 있지만 본문에 그런 정의는 없습니다(04 D10).

3.2 상태 트래픽

3.3 FP16 상태의 반올림 오차

상태를 FP16으로 저장할 때 매 토큰 반올림하는 경우와, ReplaySSM처럼 L = 16 토큰마다 한 번만 반올림하는 경우를 비교했습니다. 헤드 4개, 4,096토큰, iid 가우시안 입력, FP64 기준입니다.

상태 저장 출력 상대 오차, 빠른 헤드 (−log α ∈ [0.01, 0.05]) 느린 헤드 (−log α ∈ [2e-5, 2e-4])
FP16 RN, 매 토큰 8.4 × 10⁻⁴ 6.1 × 10⁻³
FP16 SR, 매 토큰 1.19 × 10⁻³ 8.5 × 10⁻³
ReplaySSM L = 16 + RN 2.1 × 10⁻⁴ 1.5 × 10⁻³

  • "덜 자주 양자화해서 오차를 줄인다"는 주장은 toy에서 성립합니다. 오차가 3.5–4배 줄었고, 반올림 횟수가 1/16이 되면 랜덤워크 오차가 √16 = 4배 줄어드는 것과 맞습니다.
  • stochastic rounding(SR)의 이점은 이 toy에서 보이지 않습니다. iid 입력에서는 SR이 RN보다 오차가 약 1.4배 큽니다. SR의 장점(작은 갱신이 반올림에 묻히는 stagnation 방지, 기댓값 비편향)은 갱신이 반 ulp보다 작은 경우에만 드러납니다. 보고서는 FP16+SR을 채택했지만, RN과 직접 비교한 결과는 이 보고서에 없습니다. 근거는 선행 보고서(Super 3, Ultra 3)에 있을 수 있으나 확인하지 않았습니다.

4. MOPD advantage의 성질 (§3.6, Eq. 1–2)

  1. reverse KL의 토큰 분해. 학생 샘플 y ~ π_S에서 Â = log π_T(y) − log π_S(y)의 기댓값은 −D_KL(π_S ‖ π_T)입니다. 학생이 교사보다 확률을 과하게 준 토큰은 음의 신호, 덜 준 토큰은 양의 신호를 받습니다. 교사가 낮게 보는 영역을 학생이 피하게 만드는 mode-seeking 성질이라, 여러 교사의 서로 다른 모드를 평균해 흐리게 만드는 위험이 forward KL보다 작습니다.
  2. proximal teacher의 하한. 교사를 α π_T + (1−α) π̄_S로 바꾸면 Â = log(α π_T/π̄_S + 1 − α) ≥ log(1−α)입니다. α = 0.2에서 log 0.8 = −0.2231입니다. 어휘 4,096, Dirichlet 분포 200쌍으로 확인한 최솟값은 −0.22314로 하한과 같았습니다. 같은 toy에서 KL(π_S ‖ π_T)의 중앙값 8.8이 KL(π_S ‖ mix)에서는 0.17로 줄었습니다. 2단계는 신호를 크게 줄인 trust-region식 갱신이고, 1단계에서 이미 교사를 흡수한 학생이 다시 크게 흔들리지 않게 하려는 장치로 읽힙니다.
  3. self-anchor는 KL 정규화입니다. 교사가 없는 환경의 프롬프트를 학생 시작점 복사본으로 보내면, 그 도메인에서는 D(π_S ‖ π_start)를 줄이는 신호만 생깁니다. 2단계에서 에이전트·추론 교사를 은퇴시키고 그 환경을 self-anchor로 돌린 것(§3.6)은 "이미 배운 능력을 잊지 않게 묶어 두기"입니다.

3. 이 저장소의 다른 논문과의 관계

솔직히 말하면 직접적인 방법론 연결은 약합니다. 이 저장소의 로봇 논문들은 2–3B 규모 VLM이나 비디오 생성 모델을 백본으로 쓰고, 실시간 제어 지연이 핵심 제약입니다. Super VL은 활성 12B, 체크포인트 75–249 GB라 로봇 위에서 돌리는 백본 후보가 아닙니다. 연결 지점은 "오프라인 도구"와 "학습 레시피" 쪽입니다.

폴더 그 논문의 핵심 Super VL과의 관계
thinkworld/ Qwen3-VL-2B VLA가 손목 움직임 토큰(CoD)을 생성하고, 예측-관찰 일치 보상으로 GRPO 둘 다 VLM 자체를 RL로 고칩니다. ThinkWorld의 결과 기반 보상과 Super의 MOPD는 상보적입니다. 과제별로 RL한 교사 여러 개를 한 학생으로 합치는 MOPD 레시피(§3.6)는, 과제별 VLA 정책을 하나로 합칠 때 그대로 참고할 수 있습니다. 다만 2B 학생에 MOPD를 쓴 증거는 이 보고서에 없습니다
pacevla/ GR00T N1.5 action expert에 속도 모드 decoder 4개, LVLM(Gemini 3.8 Flash) 라벨로 학습한 judge·라우터 PaceVLA는 데이터셋 전체의 chunk 라벨링을 상용 API로 했습니다. Super VL(OpenMDW, 비디오 입력, 1M 문맥)은 이 오프라인 라벨러를 자체 호스팅 모델로 바꾸는 후보입니다. 다만 로봇 국면 판정 정확도는 이 보고서의 평가에 없습니다
agentic_wam/ 코드·미래 영상·행동을 MoT 하나에서 함께 denoise (SDAR-1.7B 코드 LM, Cosmos-Predict2.5-2B, Qwen3-VL-2B ViT). 하이브리드 모드에서 Molmo·SAM 3·GraspNet 사용 AW-0의 "코드로 계획" 부분은 작은 LM을 씁니다. Super VL의 시각 도구 사용(SpatialClaw, crop·zoom·SAM3 호출)과 에이전트 학습은 도구를 호출하는 상위 계획기 쪽과 맞닿습니다. 지연 0.23 s 수준의 joint denoising과는 시간 규모가 다릅니다
hydra0/ 범용 비디오 world model(Cosmos 2.5, Wan2.2)로 행동을 이미지 평면 점 궤적(action flow)으로 생성 직접 관계는 거의 없습니다. 같은 NVIDIA 연구 생태계이고, 보고서가 "© NVIDIA All rights reserved"라 그림을 게시하지 못한다는 라이선스 처리만 같습니다

하이브리드 SSM 관점의 연결. 로봇 정책의 긴 이력(수천 프레임 관측)을 다룰 때, KV는 문맥에 비례해 늘고 Mamba 상태는 고정입니다. Super의 서빙 분석(§5.2–5.4)과 03 §2의 요청당 메모리 계산은 하이브리드 백본 VLA를 설계할 때 메모리 예산을 잡는 근거가 됩니다.
