## 1. Abstract가 주장하는 것

1. **비용:** 뒤쪽 토큰은 앞쪽 토큰보다 생성 비용이 큽니다. 오픈 모델에서는 그 차이가 최대 7배입니다.
2. **정확도:** 자주 압축(compaction)하면 장기 과제와 긴 입력 과제 모두에서 정확도를 거의 잃지 않습니다.
3. **극단:** 한 문맥에서 행동을 하나만 하고 바로 압축해도(SAC) SWE 과제 성능이 무너지지 않습니다.
4. **제안:** 그래서 semantic state space model(SSSM)이라는 개념을 내놓고, 긴 문맥 모델이 필요한지 묻습니다.

질문은 RQ0 "긴 문맥이 필요한가?"이고, 이를 세 개로 나눕니다(§1).

| RQ | 질문 | 답의 근거 |
|---|---|---|
| RQ1 | 장기 과제(LCW1)를 긴 문맥 없이 풀 수 있나 | §3, Fig. 5, Table 3–8 |
| RQ2 | 긴 입력 과제(LCW2)를 긴 문맥 없이 풀 수 있나 | §4, Fig. 6, Table 11–17 |
| RQ3 | 문맥마다 행동을 하나만 해도 장기 과제를 풀 수 있나 | §5, Table 2 |

논리의 뼈대는 이렇습니다. 긴 입력 과제는 입력을 파일로 두고 선택해서 읽는 도구를 주면 장기 과제로 바뀝니다(§1, LCW2 → LCW1). 장기 과제는 대화 이력을 압축하면 짧은 문맥으로 풀 수 있습니다. 따라서 두 가지 모두 긴 문맥이 필요 없다는 결론입니다.

## 2. 방법

### 2.1 정의 (§2.1)

- **긴 문맥:** 당시 주요 모델의 창(약 256K 토큰)에서 상당한 비율을 차지하는 문맥. **짧은 문맥:** 대략 16K–50K.
- Table 1은 문학 작품 길이와 모델 창을 비교합니다. 단어당 약 1.33토큰으로 환산했습니다. 『노인과 바다』 37K, 『위대한 개츠비』 64K 토큰처럼, 짧은 창에도 상당한 분량이 들어간다는 주장입니다.

### 2.2 문맥 관리 세 가지 (§2.4.1, Fig. 3)

| 방식 | 동작 |
|---|---|
| FHA (Full-History Accumulation) | 행동과 관찰을 한 대화에 계속 붙입니다. mini-swe-agent 기본값이고 기준선입니다 |
| EoCC (End-of-Conversation Compaction) | 문맥이 압축 임계값을 넘으면 모델에게 인계 요약(handoff recap)을 쓰게 하고, 시스템 프롬프트 + 과제 + 요약으로 새 대화를 시작합니다. "총 문맥 한도 / 압축 임계값"(예: 24K / 18K)으로 적습니다. 한도는 요약 차례를 위한 여유이고, 그 안에 요약이 끝나지 않으면 대화를 끝냅니다 |
| SAC (Single-Action Compaction) | 대화마다 과제와 현재 의미 상태를 받아 행동 하나를 하고, 결과를 본 뒤 상태를 고쳐 쓰고, 대화를 버립니다 |

긴 입력은 `input01.txt` 같은 파일로 두고, 에이전트가 `sed`, `awk`, `head`, `grep`으로 필요한 부분만 읽게 합니다(§2.4.2, 부록 E).

### 2.3 좋은 압축의 조건 (부록 A, 부록 G)

저자들은 압축을 요약의 특수한 경우로 보면 손해라고 말합니다. 요약은 모든 사실에 같은 무게를 주고 반복된 부분을 과하게 강조합니다. 정확도를 가장 잘 지킨 압축에는 다음이 들어 있었습니다.

1. 과제 원문(또는 거의 그대로).
2. 지금 하고 있는 일, 의도, 다음 단계.
3. 앞으로 실행에 직접 필요한 산출물: 과제를 쪼갠 계획, 완료 조건, 관련 정보나 그 정보가 있는 위치.

즉 실행 이력의 줄거리가 아니라 **다음 실행을 위한 선별 브리핑**입니다. mini-swe-agent용 압축 프롬프트(G.1)는 6항목입니다: Objective, Established facts, Applied changes, Verification, Dead ends, Remaining plan. 다만 `{persistence}`, `{handoff_details}`, `{submission_reminder}` 같은 자리표시자의 내용은 공개하지 않았습니다. 그래서 프롬프트는 윤곽(outline)만 있습니다.

### 2.4 비용 추정 (부록 B, §2.5)

1. **처리량 측정:** H100 노드(Qwen 3 Coder Next 8장, GLM 5.2·Kimi K2.6 16장)에서 vLLM으로 서빙합니다. 창 크기 W마다 요청 길이를 공유 토큰열의 중첩 접두사에서 균일하게 뽑고, 각 요청이 정확히 1,024토큰을 생성하게 합니다. prefix caching을 켜고, KV 선점(preemption)이 없는 범위에서 가장 높은 처리량을 보고합니다(Fig. 4).
2. **비율:** r_M = T_M(256K) / T_M(16K) = 0.2772(GLM 5.2), 0.1777(Kimi K2.6), 0.1439(Qwen 3 Coder Next) (Eq. 1). 역수가 본문의 3.6배, 5.6배, 7배입니다. 평균을 반올림해 r = 0.20을 씁니다.
3. **닫힌 모델에 적용:** 표준 소매 출력 단가를 최대 창(Opus 4.5 200,000, GPT 5.6 Sol 272K)에 고정하고, 16K에서 r배가 되도록 선형 보간합니다. 16K보다 작은 W는 16K로 자릅니다(Eq. 2).
   C_out(W) = C_out(W_max) · [ r + (1 − r) · (max(W, 16K) − 16K) / (W_max − 16K) ]
4. 입력 단가는 출력의 1/5, 캐시 입력은 입력의 1/10로 둡니다(Eq. 3). EORC = I·C_in + H·C_cached + O·C_out (Eq. 4).
5. **기준선(FHA)은 W = W_max**로 계산합니다(부록 B). 그래서 기준선의 EORC는 명목 비용과 같습니다.

로컬 측정(Fig. 2)은 DGX Spark에서 요청 하나씩, 길이를 늘려 가며 다음 1,024토큰의 평균 토큰 간 지연을 잽니다. 본문은 "여러 모델에서 뒤쪽 토큰 생성이 약 2배 오래 걸린다"고 씁니다.

### 2.5 모델과 벤치마크 (§2.2, §2.3)

- **작업 모델(닫힌 모델):** Claude Opus 4.5, GPT 5.6 Sol. 단가는 2026-09-29 기준 Opus $5 / $0.50 / $25, GPT $4 / $0.40 / $20(새 입력 / 캐시 입력 / 출력, 100만 토큰당).
- **처리량 측정용:** GLM 5.2, Kimi K2.6(INT4 expert, BF16 활성값, Kimi는 FP8 KV), Qwen 3 Coder Next(BF16).
- **로컬(DGX Spark):** Qwen 3.6 27B(NVFP4, Gated DeltaNet:full attention 3:1), Qwen 3 Coder Next(NVFP4, 같은 하이브리드, 80B-A3B), Gemma 4 31B(Q4_K_M, 1024 슬라이딩 창 + 전역), Step 3.7 Flash(198B-A11B, Q3_K_M), MiniMax M2.7(230B-A10B, IQ3_XXS, 전부 full attention).
- **장기 과제:** SWE-bench Verified 500, SWE-bench Multilingual 300, Terminal-Bench 2.1 89, FRAMES 824, τ²-bench 184, BFCLv3 200.
- **긴 입력 과제:** LongBench v2 503, LOONG 1,600, AA-LCR 100, NIAH 125(16K–약 500K), RULER 13과제(256K·500K), Counting-Stars 192(4K–128K), BABILong 550(64K–1M).

### 3.5 SSSM 제안 (§5.1)

SSSM은 (1) 대화 상태의 자연어 설명을 이해하고, (2) 다음 행동을 추론하고, (3) 행동하고, (4) 결과를 기록하고, (5) 다른 추론 인스턴스가 이어받을 수 있게 상태 설명을 고쳐 쓰도록 후학습한 모델입니다. 신경망 내부 상태를 넘기는 SSM과 달리 읽을 수 있는 자연어 상태를 넘긴다는 점에서 "semantic"이라고 부릅니다. 학습한 모델은 없고 개념 제안입니다.

## 4. 저자가 밝힌 한계와 내가 본 한계

**저자가 밝힌 것(§3.1, §6):** 압축은 손실이 있습니다. 긴 문맥이 도움이 되는 과제가 없다고 증명하지 않았고, 모든 과제를 짧은 문맥으로 풀 수 있다는 증명도 아닙니다.

**논문에 적히지 않은 것(자세한 수치는 `03`, `04`):**

1. **"뒤쪽 토큰이 7배 비싸다"는 두 가지 양을 섞습니다.** 7배는 포화 서빙에서 창을 256K로 설정했을 때와 16K로 설정했을 때의 토큰당 비용 비율이고, 요청 길이를 균일하게 뽑은 조건의 값입니다(Fig. 4). 위치별 지연은 Fig. 2의 약 2배입니다. 이 비율은 구조(SSM 상태 대 KV 비중, 활성 파라미터)와 서빙 한계에 따라 1배에서 15배까지 달라집니다(`03` §1).
2. **절감 배수 대부분은 가정한 r에서 나옵니다.** 지금의 평탄한 단가로는 압축이 GPT 비용을 22개 설정 중 21개에서 늘립니다(`04` C5). 오픈 모델 세 개에서 잰 r = 0.20을 구조를 모르는 닫힌 모델에 그대로 적용했습니다.
3. **기준선을 창 전체 가격으로 매깁니다.** FHA 문맥 대부분은 짧은데(Opus SWE-V 최종 길이 중앙값 32K) 배수 1을 매깁니다. 같은 규칙으로 요청마다 값을 매기면 절감 폭이 크게 줄어듭니다(`03` §3).
4. **긴 입력 기준선이 창보다 깁니다.** RULER 입력은 모두 Opus 창(200K)보다 길고, NIAH·BABILong도 일부가 넘습니다. 기준선이 넘친 입력을 어떻게 처리했는지(잘라냈는지) 적혀 있지 않습니다(`04` C11).
5. **단일 실행, 유의성 검정 없음.** 44개 장기 과제 차이 중 p < 0.05는 3개입니다. "최고 EoCC"는 4개 설정 중 최댓값이라 우연만으로도 평균 +2%p 이상이 나옵니다(`04` C8).
6. **관련 연구 절이 없습니다.** 에이전트 메모리·압축 계열(MemGPT 등)과 RAG 기준선을 인용하거나 비교하지 않습니다(`02` §1).
