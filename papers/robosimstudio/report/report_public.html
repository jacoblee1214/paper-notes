핵심 요약

  1. 무엇인가: Newton 위에 solver·접촉 모델·물성을 편집 가능한 항목으로 드러낸 Real2Sim 도구다. 사람은 브라우저 studio와 힘 피드백 리더 암으로, 코딩 에이전트는 저장하면 다시 빌드되는 live 페이지와 CLI로 같은 장면을 고친다.
  2. 논문보다 저장소가 실체다: 정량 결과가 거의 없고, Table 1은 RSS가 10/10인 기능 목록이다. 반면 공식 저장소(Apache-2.0)는 설치 문서, 예제, 테스트, CPU 경로까지 갖춘 쓸 수 있는 도구다.
  3. 핵심 자산은 비공개다: Fig. 5의 18개 과제 정의, GaP 닦기 정책과 30개 배치, UR5e, 실제 로봇 코드가 공개 저장소에 없다. 논문 결과는 재현할 수 없다.
  4. 공개 twin은 물리적 잡기를 우회한다: 마찰만으로는 스펀지가 69–226 mm 미끄러져 닦인 비율이 0.72에 그친다. 그래서 폼 노드 106개를 손에 고정(latch)해 0.96을 얻는다. 영상 속 20 kPa 스펀지 대신 80 kPa 폼도 쓴다. 같은 저장소의 에이전트 규칙은 latch를 금지한다.
  5. 영상만으로는 물성이 정해지지 않는다: toy로 계산하면 1080p 영상에서 E > 100 kPa는 사실상 식별 불가하고, 80 vs 100 kPa는 0.36σ 차이다. 힘 관측은 오차가 일정하다(0.4 kPa). 강성을 "맞추기"보다 "변형"한 선택과 힘 피드백의 동기를 뒷받침한다.
  6. GaP 곡선의 29%·71%는 30개 배치의 성공률로 나올 수 없는 값이다. 닦인 면적 같은 연속량으로 읽어야 한다.
  7. 구현 가능성: Linux x86-64 + Python 3.12가 기준이다. 이 맥에서는 CPU 경로로 강체 장면과 에이전트 루프를 시험할 수 있어 보이지만, 설치 승인이 필요하다. 변형체 대부분, 경로 추적 렌더러, GaP·cuRobo는 NVIDIA GPU가 필요하다.

1. Abstract (한 줄 요약과 주장)

한 줄 요약: 시뮬레이터의 solver, 접촉 모델, 물성 값을 명시적으로 드러내고 바로 고칠 수 있게 만든 Newton 기반 도구입니다. 사람(브라우저 화면, 슬라이더, 힘 피드백 리더 암)과 코딩 에이전트(Claude Code, Codex)가 같은 장면을 고쳐 가며, 실제 영상과 비슷하게 움직이는 다중 물리 시뮬레이션(Real2Sim)을 빠르게 만들게 하려는 것입니다.

기여는 세 가지입니다(Sec. 1).

  1. 접촉 모델과 물성을 바꿀 수 있는 contact-rich 조작용 시뮬레이션 도구 RoboSimStudio(RSS)
  2. 사람과 코딩 에이전트가 함께 쓰는 Real2Sim 인터페이스
  3. 시각·힘 피드백으로 만든 조작 과제 18개, 그리고 스마트폰 영상에서 코딩 에이전트가 다중 물리 시뮬레이션을 만든 Real2Sim2Real 파일럿 1건

논문은 스스로를 "개발 중인 시스템과 파일럿 연구"라고 부릅니다(Sec. 5). 정량 실험은 거의 없고, 대부분의 결과는 정성적 시연입니다.

2. Method

2.1 구조 (Fig. 2, Sec. 3)

영상·사진 (사람·로봇 시연, 스마트폰)
        │  사람: 브라우저 studio (Viser) — 선택·드래그·인스펙터 슬라이더
        │  코딩 에이전트: scene.py를 고치고 실행·관찰하는 반복 루프
        ▼
장면 = 로봇 + 물체 + 물리 배치(arrangement)
   물체는 "무엇인지"(강체, 관절, 천, 케이블, 스펀지 …)만 선언
   장면이 "어느 solver가 어떤 물리를 맡는지" 선언 → 바꿔도 과제 코드는 그대로
        ▼
Newton (Warp)  ─ 관절·강체: MuJoCo-Warp   ─ 천·케이블: VBD
        └─ 외부 엔진 co-sim: SuperDex(FEM 스펀지), Genesis   ← 접촉력·자세·wrench 교환
        ▼
변형(물성 E, 공간 배치) → Graph-as-Policy(GaP)로 정책 개선 → 실제 로봇

논문 Fig. 2: 자산 처리, 로봇 인터페이스, Newton 다중 물리 백엔드와 외부 solver(Genesis, SuperDex).

2.2 로봇 인터페이스

Franka Panda, UR5e, 단팔·양팔 YAM의 공통 인터페이스가 있습니다(Sec. 3). IK는 PyRoKi 같은 solver를 바꿔 끼울 수 있고, 계획은 cuRobo를 씁니다. 정책은 관절 공간이나 엔드이펙터 공간으로 명령합니다. 조작 물체의 privileged 상태는 로봇이 볼 수 있는 관측과 분리합니다.

2.3 다중 물리와 결합

기본값은 다음과 같습니다. 관절 로봇은 MuJoCo-Warp, 케이블과 천은 Vertex Block Descent(VBD), 연성체는 외부 엔진(SuperDex, Genesis)과 co-sim입니다. Newton 내부 solver끼리는 접촉력을, 외부 엔진과는 자세와 접촉 wrench를 주고받아 결합합니다. solver, 결합 방식, 접촉 모델, 재료 값은 장면의 명시적 항목이라 과제를 다시 쓰지 않고 바꿀 수 있습니다(Fig. 3).

논문 Fig. 3: 다섯 과제의 solver 배치. MuJoCo-Warp(보라), FEM(청록), VBD(주황).

2.4 사람용 인터페이스 (Fig. 4)

Viser 기반 브라우저 studio입니다. 물체를 선택·드래그·검사하고 로봇 팔을 직접 움직일 수 있습니다. 인스펙터는 물성을 단위·범위와 함께 보여 주고, 실행 중 바꿀 수 있는 값과 장면을 다시 만들어야 하는 값을 구분해 표시합니다.

논문 Fig. 4: 수건 인스펙터와 휨·늘어남 강성 네 조합의 같은 접기.

2.5 에이전트용 인터페이스

코딩 에이전트는 사람과 같은 루프를 돕니다. 장면을 고치고, 행동을 실행하고, 결과를 관찰합니다. RSS는 rollout을 로봇 동작 primitive로 나누고, 시뮬레이터 상태를 시공간 텍스트 피드백으로 바꿔 줍니다. 피드백에는 목표 오차, 물체 움직임, 접촉 사건, 잡기·미끄러짐, 과제 진행도가 들어갑니다. 사람은 에이전트가 작업하는 동안 비동기로 같은 화면을 보며 값을 고치거나 지시할 수 있습니다(human-in-the-loop).

3. 사례 연구 (Sec. 4)

3.1 시각 피드백으로 하는 사람 Real2Sim (Sec. 4.1, Fig. 5)

사용자가 자산을 고르고 배치하고 물리 모델을 고른 뒤, 실제 거동과 시뮬레이션이 정성적으로 맞을 때까지 접촉·재료 값을 조정했습니다. 이렇게 과제 18개를 만들었습니다. 예로 든 것은 세 가지입니다.

  • 커넥터 삽입: USB-C를 1 mm 미만 여유로 꽂으려고 메쉬 기반 접촉과 충돌 해상도를 조정했습니다.
  • 잎 누르기: 쉘 시뮬레이션으로 얇은 잎의 휨과 회복을 표현했습니다.
  • 띠 연마: 접촉력에서 Preston 식으로 재료 제거량을 계산했습니다.

본문은 한 문장 안에서 "세 과제"와 "다섯 예"를 함께 쓰고, 실제로는 셋만 나열합니다. 편집 흔적으로 보입니다.

3.2 힘 피드백으로 하는 사람 Real2Sim (Sec. 4.2, Fig. 6)

저가 리더 암(논문은 GELLO[58] 인용)으로 시뮬레이션 로봇을 조종하고, 시뮬레이션 접촉을 리더 모터 토크로 되돌려 줍니다. 명령 자세와 시뮬레이션 자세의 차이가 피드백 신호입니다. 시뮬레이션 지연을 접촉으로 착각하지 않도록 속도 의존 deadband를 두고, 시뮬레이션이 멈추거나 뒤처지면 피드백을 끕니다. 그리퍼는 명령값이 아니라 측정된 열림을 씁니다. 공구 걸기 과제를 시연했지만 정량 결과는 없습니다.

3.3 에이전트 Real2Sim2Real (Sec. 4.3, Fig. 7)

양팔 스펀지 닦기 과제입니다. 한 팔이 막대를 잡고 다른 팔이 폼 스펀지로 마커 줄을 지웁니다.

단계 보고 내용
구축 CAD도 보정 카메라도 없는 스마트폰 영상 하나로 Claude Fable 5.1(Claude Code)과 GPT-6 Astra(Codex)가 각자 "약 1시간"에 다중 물리 시뮬레이션을 만듦. 한 에이전트는 56분에 검증 완료(14분 팔·막대, 42분 첫 닦기, 51분 배경, 56분 검증)
물리 MuJoCo-Warp(Newton) + SuperDex(스펀지 FEM). 접촉력과 압력 분포 확인
변형 스펀지 강성 6·20·100 kPa, 막대·스펀지 배치 30개
정책 GaP가 14번 반복으로 시뮬레이션에서 닦인 면적을 0% → 100%로 올림(반복 9: 29%, 11: 71%)
실제 개선된 정책을 실제 로봇에서 실행해 닦기 완료. 한 rollout에서는 시뮬레이션에서 고정했던 막대 받침이 밀려나 실패
정제 실패 영상과 설명을 받은 에이전트가 고정 제약을 자유 강체로 바꿈 → 수정된 시뮬레이션은 막대가 밀리고 기우는 현상을 재현

4. 해석

  • 이 논문의 실체는 도구입니다. 성능 표가 없고, Table 1은 다른 프레임워크와의 기능 비교입니다. 그런데 이 표에서 RSS는 10개 행이 모두 ✓이고, RSS만 ✓인 5행은 전부 이 논문이 정의한 워크플로입니다(04 C1). 비교라기보다 기능 목록에 가깝습니다.
  • GaP 곡선의 단위가 그림마다 다릅니다. Fig. 1은 y축을 "completion rate"라고 쓰고, 본문과 Fig. 7f는 "simulated wiped area"라고 씁니다. 29%와 71%는 30개 배치의 성공 비율로는 나올 수 없는 값입니다(k/30 = 26.7, 30.0, 70.0, 73.3%). 따라서 닦인 면적 같은 연속량이거나 다른 분모입니다(04 C2).
  • 실제 로봇 결과는 시행 횟수가 없습니다. "실제 로봇에서 닦기를 완료했다"와 "한 rollout이 실패했다"만 있습니다. 시뮬레이션-실제 일치도는 "주로 정성적 관찰"이라고 저자들도 씁니다(Sec. 5).
  • 공식 저장소가 논문보다 훨씬 구체적입니다. 다음 사실은 저장소에서만 드러납니다.
    • 공개 twin의 스펀지는 friction만으로 잡히지 않습니다. 그래서 패드 주변 폼 노드 106개를 손에 고정(latch)하고, 영상의 부엌 스펀지(약 20 kPa) 대신 80 kPa 폼을 씁니다(04 D3·D4).
    • 18개 과제 대부분과 UR5e, GaP 닦기 정책, 30개 배치는 공개 저장소에 없습니다(04 D1·D2·D6).

5. Limitations

5.1 저자가 밝힌 한계 (Sec. 5)

  • 개발 중인 시스템이고 파일럿 연구입니다.
  • 에이전트의 시뮬레이션 구축은 RSS가 제공하는 재료 모델, 물리 결합, 로봇 자산에 의존합니다.
  • 외부 엔진 co-sim은 계산 부담이 있습니다.
  • sim-to-real은 과제 하나로만 평가했고, 일치도는 주로 정성적입니다.
  • 향후 과제로 시뮬레이션 정확도, 접촉력, 물체 궤적, 구축 시간, 실제 성공률의 체계적 정량 평가를 들었습니다.

5.2 분석하면서 추가로 발견한 한계와 의문점

  1. "영상과 맞을 때까지"의 판정 기준이 없습니다. 맞았다는 판단이 눈으로 하는 정성 비교입니다. 영상만으로는 강성 같은 값이 잘 정해지지 않습니다. toy로 계산하면 1080p 영상에서 판독 잡음이 0.5 px만 있어도, E가 약 100 kPa를 넘으면 E 추정의 상대 표준오차가 50%를 넘습니다. 80 kPa와 100 kPa는 0.4σ 차이라 구분되지 않습니다(03 §2). 논문이 강성을 "맞추기"보다 6–100 kPa로 "변형"한 이유로 읽을 수 있습니다.
  2. 공개 twin은 물리적 잡기를 우회합니다. 마찰만으로는 세 take 모두 폼이 손에서 69–226 mm 미끄러졌고, 닦인 비율도 0.69–0.76에 그쳤습니다. 30회를 더 시도해도 미끄럼을 10 mm 아래로 줄이지 못했습니다(04 C4). 같은 저장소의 에이전트 작업 규칙은 latch·weld·attachment를 금지합니다(examples/live/AGENTS.md, 2026-10-22 추가). 즉 논문 시점의 데모가 이후 규칙을 어깁니다.
  3. 강성 변형 범위가 실제 잡기 가능 범위와 겹치지 않습니다. Fig. 7e의 6·20 kPa는 공개 twin의 집게 조건에서 스펀지가 패드 사이로 흘러나가는 범위입니다(04 C6). GaP가 이 범위에서 어떻게 닦았는지는 공개 자료로 알 수 없습니다.
  4. 에이전트의 기여와 사람의 기여가 분리되지 않았습니다. "human-in-the-loop"를 강조하지만, 56분 동안 사람이 몇 번 개입했는지 기록이 없습니다. 저장소 README의 팁("가끔 물리와 기하를 재구성하라고 상기시켜라")은 개입이 필요했다는 뜻입니다.
  5. 재현에 필요한 자산 상당수가 비공개입니다. 18개 과제의 정의(테스트 코드가 vabar 컬렉션이라고 부르는 것), UR5e, 실제 로봇 실행 코드, GaP 닦기 그래프가 없습니다. 논문 시점에는 CPU 실행도 지원되지 않았습니다(2026-10-18 추가).

03. 수치 재계산과 toy 해석

스크립트는 analysis/table_check.py(결과 table_check_results.json)와 analysis/identifiability_toy.py(결과 identifiability_toy_results.json)입니다. 모두 numpy·scipy로 단일 스레드에서 1초 안에 끝납니다. 공식 데모 수치는 저장소 examples/08_demos/wipe_the_bar/(커밋 81f57c9)의 README와 bar.py에서 옮겼습니다.

1. Preston 마모: 공개 twin의 마커 줄 지우기 (C5)

공개 twin은 마커 줄을 2.5 mm 셀로 나누고, 각 셀의 잉크를 Preston 법칙으로 줄입니다.

d(ink)/dt = − k_p · p · v      (k_p = 1.2×10⁻² 1/(Pa·m), p < 300 Pa이면 마모 없음, ink ≤ 0.1이면 "clean")
  • 주석 검산: bar.py는 "4 N, 30 mm/s 스트로크면 셀 하나를 약 2초에 지운다"고 적었습니다. 4 N을 스펀지 면(50 × 75 mm)에 고르게 나누면 평균 압력이 1,067 Pa이고, 잉크 0.9를 지우는 데 0.9 / (k_p · p · v) = 2.34 s가 걸립니다. 주석과 맞습니다.
  • 한 스트로크의 마모는 속도와 무관합니다. 스펀지 긴 변 L(75 mm)이 셀을 지나는 시간은 L / v이므로, 한 번 지날 때 마모량은 k_p · p · L입니다. 평균 압력이면 0.96이라 한 스트로크로 거의 지워집니다. 측정된 첫 스트로크 0.91과 같은 자릿수입니다.
  • 최대 압력은 평균과 두 자릿수 차이가 납니다. 측정 최대 압력은 84 kPa로 평균의 약 80배이고, 이 압력이면 셀 하나가 0.03초에 지워집니다. "닦인 비율"은 압력이 몰린 곳과 300 Pa 문턱 아래 띠의 비율에 따라 정해지는 지표입니다.
  • 함의: 네 번 닦아도 0.955–0.959에 머무는 것은 문턱 아래 띠와 접촉이 끊기는 셀 때문으로 보입니다(가설). 논문의 "닦인 면적 100%"는 GaP가 만든 다른 rollout의 값이라 직접 비교할 수 없습니다. 다만 같은 법칙과 문턱을 쓴다면 100%는 문턱 아래 셀이 하나도 없어야 나오는 값입니다.

2. 영상만으로 강성을 맞출 수 있는가 (식별성 toy)

논문은 사람이나 에이전트가 영상과 시뮬레이션을 눈으로 비교해 물성 값을 고친다고 씁니다(Sec. 4.1, 4.3). 가장 단순한 모델로 그 비교의 해상도를 계산했습니다.

  • 모델: 스펀지 면을 4 N으로 누를 때 선형 압축 δ = F h / (E A)입니다(A = 50 × 75 mm, h = 30 mm).
  • 시각 관측: 화면 폭이 0.6 m인 영상에서 δ를 픽셀로 읽습니다. 판독 잡음은 0.5 px와 2 px 두 경우입니다.
  • 힘 관측: 알려진 2 mm 압입에서 힘을 0.1 N 잡음으로 읽습니다.
  • 표준오차: 해석식은 SE_vision(E) = σ_δ · E² · A / (F h), SE_force = σ_F · h / (A · δ_c)이고, Monte Carlo로 확인했습니다. 20 kPa에서 해석 1.95 kPa, Monte Carlo 1.96 kPa입니다.
E 압축 δ 1080p에서 4K에서
6 kPa 5.33 mm 17.1 px 34.1 px
20 kPa 1.60 mm 5.1 px 10.2 px
80 kPa (공개 twin) 0.40 mm 1.3 px 2.6 px
100 kPa 0.32 mm 1.0 px 2.0 px

  • 영상으로는 E가 약 100 kPa를 넘으면 사실상 정해지지 않습니다. 상대 SE가 50%를 넘는 경계는 1080p·0.5 px에서 104 kPa, 1080p·2 px에서 26 kPa, 4K·0.5 px에서 206 kPa입니다.
  • 영상에서 구분되는 차이와 구분되지 않는 차이가 있습니다. Fig. 7e의 20 kPa와 100 kPa는 1080p·0.5 px에서 5.8σ 차이라 구분됩니다. 반면 공개 twin의 80 kPa와 100 kPa는 0.36σ 차이라 영상으로는 같습니다.
  • 힘 관측은 오차가 E와 무관하게 일정합니다(0.4 kPa). 그래서 단단한 물체일수록 힘 관측이 유리하고, 무른 물체(10 kPa 미만)에서는 오히려 영상이 낫습니다.
  • 해석: 논문이 힘 피드백을 따로 둔 동기(Sec. 4.2 "관찰만으로는 접촉을 판단하기 어렵다")와 강성을 맞추는 대신 넓게 변형한 선택(Fig. 7e)을 정량적으로 뒷받침합니다. 반대로, 에이전트가 "영상과 맞는 시뮬레이션"을 만들었다는 주장은 기하와 운동에는 강하고 물성에는 약하다는 뜻입니다.
  • 한계: 선형 일축 압축, 고정 시야, 판독 잡음은 모두 가정입니다. 실제 영상의 원근, 가림, 흐림은 이보다 나쁩니다.

3. 강성과 잡기: 공개 twin이 80 kPa를 쓴 이유 (C6)

bar.py의 FOAM 주석에 따르면, 80 kPa 폼은 패드당 8.6–8.9 N으로 50 mm에서 45.5 mm로 눌립니다(변형률 9%). 이를 선형 탄성으로 보면 유효 패드 면적은 약 12 cm²입니다. 같은 조건에서 각 강성의 예상 변형률은 다음과 같습니다.

E 예상 변형률 저장소의 관찰
6 kPa 120% (불가능, 완전히 눌림) –
20 kPa (영상 속 부엌 스펀지) 36% "패드 사이로 흘러나가 집게가 맞닿았다"
80 kPa (공개 twin) 9% 잡히지만 마찰만으로는 닦는 동안 미끄러짐 → latch
100 kPa 7% –

선형 추정은 20 kPa에서도 잡힐 것처럼 보이지만, 실제 FEM에서는 큰 변형 때문에 폼이 흘러나갔습니다. 어느 쪽이든 Fig. 7e의 6·20 kPa는 공개 twin의 집게 조건으로 스펀지를 들 수 없는 범위입니다. GaP가 이 강성 변형에서 어떻게 닦았는지(latch를 썼는지)는 공개 자료로 알 수 없습니다.

4. GaP 곡선의 분모 (C2)

Fig. 1과 Fig. 7f의 값은 반복 0·9·11·14에서 0·29·71·100%입니다. 이 네 값이 k/n을 정수 %로 반올림해서 나오는 n을 60까지 찾으면 다음과 같습니다.

n = 7, 14, 17, 21, 24, 28, 31, 34, 35, 38, 41, 42, 45, 48, 49, 51, 52, 55, 56, 58, 59

30은 없습니다. 30개 배치의 성공 비율이라면 29% 대신 26.7%나 30.0%, 71% 대신 70.0%나 73.3%가 나와야 합니다. 따라서 이 곡선은 본문 말대로 닦인 면적 같은 연속량이거나, 30개가 아닌 다른 개수에 대한 비율입니다. Fig. 1의 y축 이름 "completion rate"는 성공률로 읽히기 쉬워서 오해의 여지가 있습니다.

5. Table 1의 구조 (C1)

RSS는 10개 행이 모두 ✓입니다. 다른 다섯 프레임워크는 2–4개입니다. RSS만 ✓인 행은 5개입니다(구조화된 에이전트 피드백, 사람-에이전트 공동 정제, 영상 기반·힘 피드백·실패 기반 Real2Sim). 모두 이 논문이 정의하고 구현한 워크플로입니다. 나머지 물리 기능 5행에서 RSS의 ✓는 대부분 Newton 위에서 물려받은 것입니다. 예를 들어 Newton 자체도 강체·변형체는 ✓이고 결합은 ∼입니다.

D5 에이전트용 "시공간 피드백"의 실체는 시각 비교 수치와 gate입니다. compare.py는 사진 대비 크기 비율과 픽셀 위치 차이를, checks.py는 take의 물체 이동과 영상 timeline 대비, 빌드·유한성·가라앉음·표류 검사를 줍니다. 논문이 나열한 "접촉 사건, 잡기·미끄러짐" 텍스트 피드백을 만드는 전용 모듈은 찾지 못했습니다. 에이전트가 접촉 문제를 풀려면 ./ctl eval로 시뮬레이터 상태를 직접 읽어야 합니다(Python 실행). 기능은 있지만 논문 서술보다 원시적입니다.
D6 UR5e가 공개 저장소에 없습니다. 레지스트리는 "콘텐츠로 배포되는 로봇은 벤치마크 계층을 import해야 등록된다"고 안내합니다. 공개된 것은 Panda, YAM 계열, Robotiq 2F-85 그리퍼입니다. Fig. 5에서 UR 계열 팔이 보이는 과제는 공개 자산으로 만들 수 없습니다.
D7 힘 피드백 리더 암은 GELLO가 아니라 YAM 리더입니다. Feetech STS3215 서보, CH340 USB 어댑터, lerobot 버스 드라이버, udev 규칙과 보정 파일을 씁니다. 공개 예제의 힘 피드백 장면은 패널과 상자이고, 공구 걸기(Fig. 6)가 아닙니다. 논문의 GELLO 인용은 개념 출처로 읽어야 합니다. 하드웨어 목록은 저장소 README가 정확합니다.
D8 CPU 실행은 논문 이후에 추가됐습니다(2026-10-18, 커밋 a2fe723). CPU에서는 MuJoCo C가 팔·강체를, SuperDex가 천·가방·로프·연성체를 맡습니다. 종이·테이프·붓·MPM·물은 거부됩니다. 로프는 단방향(케이블이 닿은 것을 밀지 않음)이고, SDF·hydroelastic 접촉과 다중 world도 쓸 수 없습니다(examples/install.md). 논문의 VBD 기반 장면(케이블, 필름, 수건, 열전사)은 CPU에서 다른 물리로 대체되거나 거부됩니다.
D9 렌더러가 플랫폼에 따라 다릅니다. 경로 추적 렌더러 OVRTX(1.8 GB)는 RT core가 있는 NVIDIA GPU와 Linux·Windows에서만 씁니다. 그 밖에는 Newton의 tiled 렌더러가 collider만 그립니다. 에이전트가 사진과 렌더를 비교하는 루프(compare_still)는 RT GPU가 없으면 질감 없는 collider 그림으로 비교하게 됩니다. A100·H100·B200도 RT core가 없어 같습니다.
D10 공식 테스트 기록(README "Measured")은 RTX PRO 6000 Blackwell에서 했습니다. 닦기 데모 README는 "superdex extra와 GPU가 필요하다"고 쓰지만, 설치 문서는 SuperDex 스펀지가 CPU에서 돈다고 씁니다. 문서끼리 다릅니다. 이 맥에서 닦기 twin이 도는지는 실행해 봐야 알 수 있습니다.
D11 논문 표지(v2)의 소속 번호는 NVIDIA 1, Berkeley 2이고, 프로젝트 페이지는 Berkeley 1, NVIDIA 2입니다. arXiv 제목에는 "for Human and Agent"가 있고 PDF 제목에는 없습니다. 사소한 표기 차이입니다.

우리 분석: 공식 wipe_the_bar 데모의 latch 유무별 닦인 비율과 미끄럼(저장소 README 수치).

3. 이 저장소의 다른 논문과의 관계

논문 관계
Do as I Do (do_as_i_do/) 둘 다 "일상 영상 → 물리 시뮬레이션"입니다. Do as I Do는 영상에서 손·물체 4D 궤적과 SAM 3D 메쉬를 자동으로 복원한 뒤 MuJoCo Warp sampling으로 리타겟팅합니다. RSS는 장면 자체를 코딩 에이전트가 손으로 짓습니다. Do as I Do가 다루지 못한 변형 물체와 접촉 모델 선택을 RSS가 채우고, RSS가 수작업으로 하는 기하 복원을 Do as I Do가 자동화합니다. 서로 보완하는 관계입니다.
FlashDexRetarget (flashdexretarget/) FlashDexRetarget은 Isaac Sim 강체 장면에서 리타겟팅합니다. 둘 다 물리적이지 않은 보조를 씁니다. FlashDexRetarget은 물체를 레퍼런스로 끄는 PD 힘을 학습 중에만 쓰고 평가에서는 끕니다. RSS 공개 twin은 스펀지를 손에 고정하는 latch를 과제 내내 씁니다(04 D3). 보조를 평가에서 빼는지가 결과의 물리적 타당성을 가릅니다.
GraspSense (graspsense/) GraspSense는 SAM 3D 메쉬로 Isaac Lab 장면을 만들고 힘 지도로 파지를 고르지만, 코드상 물체는 강체였습니다. RSS의 SuperDex FEM은 GraspSense가 검증하지 못한 "벽 변형·손상" 주장을 실제 변형체로 확인할 수 있는 도구입니다.
AlphaNIST (alphanist/) AlphaNIST는 Isaac Lab에서 NIST 조립 보드를 학습합니다. RSS의 커넥터 삽입(1 mm 미만 여유)과 같은 접촉 정밀도 문제를 다룹니다. RSS는 CPU에서 SDF·hydroelastic 접촉을 쓸 수 없어, 이런 과제는 GPU가 필요합니다(04 §4).
Contact-Grounded Policy (contact_grounded_policy/) CGP는 Meta 내부 FEM 시뮬레이터로 visuotactile 정책을 학습했습니다. RSS가 쓰는 SuperDex는 Meta의 공개 암시적 FEM 엔진입니다(facebookresearch). 같은 계열인지는 확인하지 못했습니다(가설).
