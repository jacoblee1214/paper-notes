## 3. 불일치와 빈칸

판정 기호: 불일치 = 논문과 코드가 다름, 빈칸 = 논문에 없음, 미공개 = 저장소에 없음.

**D1. 점수 보너스와 감점 (빈칸, 중요).** 부록 B는 "올바른 대상에 접근했지만 조작을 끝내지 못해도 부분 의미 점수를 받고, 틀린 물체와 상호작용하면 최종 상태가 그럴듯해도 감점"이라고 설명합니다. 코드에는 이보다 많은 규칙이 있습니다.
- Scene 1: 최종 10프레임이 관계 조건과 탁상 높이를 만족하면(`final_target_ok`) IS와 ES가 각각 0.5 미만일 때 **+0.3**을 더합니다(`evaluation/scene1.py` L1209–1217, README도 "+0.3 ES 보너스"를 예로 듭니다).
- Scene 2: 쌓기, 그릇 놓기, 밀기의 최종 배치가 맞으면(`_final_target_ok_for_bonus`) 같은 조건에서 **+0.3**(`retry_bonus_delta`, L539–541, L1382–1407).
- 장면 1–3: 닫힌 그리퍼가 지정되지 않은 팔이면 마무리 단계가 만점일 때 IS와 ES에서 각각 **−0.2**(`WRONG_ARM_INTERVENTION_PENALTY`).
- Scene 4: 집기에서 받침 물체가 1 cm 이상 들리면 단계 1 ES에서 **−0.3**(L1088).
- 효과: 단계 점수가 낮아도 최종 배치가 맞는 에피소드는 IS에 0.3이 더해지므로, S1과 S2에서 IS는 "의도 단계를 통과한 정도"만의 값이 아닙니다. README는 이 조정을 "existing score adjustments"로 밝히지만 논문 본문과 부록에는 없습니다.

**D2. 단계 가중치 (빈칸/불일치, 작음).** §3.2는 마무리 단계가 점수의 20%라고 합니다. 코드: Scene 1, 2는 집기만 0.8/0.2, 놓기류 0.4/0.4/0.2(`scene1.py` L757), Scene 4의 순차 채점기는 0.4/0.4/0.2(`scene4.py` L1122 docstring), **Scene 3은 0.3/0.3/0.4**(`scene3.py` L469–471)로 마무리 단계가 따로 없습니다. 부록 B는 "Scene 1, 2, 4에서 stage3 finish"라고 적어 이 구분을 담지만, 가중치 값은 어디에도 없습니다.

**D3. 단계 관문 (빈칸).** 뒤 단계의 의도 점수는 앞 단계 의도가 만점일 때만 인정되고(`_apply_gates`), 실행 점수는 같은 단계와 앞 단계의 의도·실행이 만점일 때만 인정됩니다. 논문은 이를 서술하지 않습니다(README는 "Stage scores retain their existing prerequisite gates"). 결과로 IS는 단계 가중치의 누적 합이고, ES ≤ IS가 구조적으로 성립합니다(표 1의 160칸이 모두 그렇습니다, 03 §1.2). Scene 3 L2에서 IS ≈ 30은 단계 1 가중치 0.3과 같은 값입니다(03 §2.3).

**D4. 마무리 단계의 내용 (불일치, 중요도 중).** 논문은 "완료 후 지시와 무관한 행동을 더 하지 않아야 만점"이라고 쓰고(§3.2), 부록 E는 "지시를 마친 뒤 계속 행동"을 실패 유형으로 듭니다. 코드의 마무리 단계(`scene1.py` L1007–1068)는 (a) 비조작 팔이 작업 영역에 들어가지 않을 것, (b) 조작 팔이 시작 위치 반경 12 cm 안으로 **연속 20프레임 안정되게 돌아올 것**, (c) 완료 시점 뒤 180 단계 이내에 돌아올 것, (d) 돌아온 뒤 16 cm 밖으로 나가지 않을 것, (e) 완료 뒤 그리퍼를 다시 닫지 않을 것을 요구합니다. "멈춤"이 아니라 "홈 복귀"를 재는 조건이라, 과제를 끝내고 그 자리에서 멈춘 정책은 마무리 점수를 받지 못할 수 있습니다.

**D5. 논문에 없는 임계값 (빈칸).** 관계 판정은 거리 12 cm 이내와 기준 방향 ±45° 원뿔(`cos` ≥ cos 45°, `scene1.py` L728–731), 집기는 xy 7 cm와 들림 1 cm(`scene3.py` L475–476), 경로와 방향은 yaw 40°(의도)와 20°(실행)(`scene3.py` L484–485), 그리퍼 닫힘 0.35와 열림 0.7, 밀기 완료 0.5 cm와 단계 2 실행 2 cm입니다. 논문은 이 값을 적지 않았고 README는 일부만 적습니다. "오른쪽/뒤"를 90° 폭의 원뿔로 판정한다는 점은 관계 의미의 엄격도를 정하는 값입니다.

**D6. 평가 프로토콜 (빈칸).** 논문에는 시행 수, 시드, 정책 호출 예산이 없습니다. 코드(`evaluate.py`): `--rounds 10`(과제당), 시드 = `base_seed(42) + round x 100 + md5(과제 이름) % 1000`(모델과 무관하게 같은 과제·라운드는 같은 시드), `--max-steps 10`(정책 호출 수), `--actions-per-step 50`(호출당 실행 목표 상한), 성공해도 조기 종료 없음(`FixedHorizonEnv.check_success`가 항상 False, `simulation.py`), 기본 실행은 TOPP 기반이고 `--direct-step`은 별도 보고용입니다. 전체 5,540회(554 x 10)입니다. `predict(obs)[:actions_per_step]`는 청크를 50개까지만 자르므로, 청크가 50보다 짧은 모델은 같은 10회 호출에서 실행하는 행동 수가 더 적을 수 있습니다. 모델별 어댑터가 저장소에 없어 각 모델의 청크 길이는 확인하지 못했습니다. 표 1의 CR 값이 "과제당 10회" 격자에 맞는 것은 03 §1.3입니다.

**D7. Scene 4 L1의 과제 수 (불일치 가능성).** 코드의 Scene 4 L1 과제 등록은 `id` 1–6과 8–15의 **14개**이고 `id=7`이 없으며, README 표도 14입니다. 표 1의 Scene 4 L1 CR 열 10개는 시행 수 150(과제 15개 x 10회)에서 모두 가능하고 140에서는 1개만 가능합니다(03 §1.3). 가능한 설명은 (a) 표 1을 만들 때 L1 과제가 15개였고 공개 때 한 개가 빠졌다, (b) 과제당 시행 수나 집계가 다르다 등이며 이 자료로는 정하지 못합니다. 저자 확인이 필요합니다.

**D8. Scene 2 L3의 "왼쪽/오른쪽 그릇" 지시와 채점 대상 (불일치, 수정됨).** GitHub 이슈 #2(2026-10-14)는 `evaluation/scene2.py`의 `L2_REFERENCES`가 `green_bowl`을 "left bowl", `yellow_bowl`을 "right bowl"로 고정해 두고, 그릇을 교환한 배치 2.5와 2.6의 L3 지시가 현재 배치와 어긋난다고 보고했습니다. 이전 공개본(`a867718`, 2026-09-23)과 현재 clone을 비교하면 `evaluation/scene2.py`의 `_pick_l3_reference`만 다르고 그릇이면 현재 배치의 x좌표로 왼쪽/오른쪽을 정하도록 바뀌었습니다. 저장소의 다른 86개 파일은 같습니다. 영향 범위는 코드로 셀 수 있습니다: 배치 2.5와 2.6의 그릇 놓기 L3 과제가 각각 4개이고 Scene 2의 L3는 24개라 **8/24(33%)**입니다. 저자는 이슈에 "이전 공개본에 구버전의 Scene 2 평가 코드가 들어 있었고 수정했다"고 답했고, 논문의 평가 결과가 정확한지 묻는 후속 질문에는 "Yes"라고 답했습니다. 표 1의 Scene 2 L3이 어느 코드 버전으로 계산되었는지는 저장소에서 확인할 수 없습니다.

**D9. 저장소 이력 (참고).** GitHub의 main에는 커밋이 하나(`f642e3d`)이고, 초기 공개 커밋 `a867718`과는 공통 조상이 없습니다. 두 트리의 파일 87개 중 86개가 같고 다른 파일은 D8의 `evaluation/scene2.py` 하나입니다. 이슈 #2는 `a867718`을 인용하고 현재 main의 커밋일(2026-10-17)은 이슈 작성일(2026-10-14) 뒤입니다. 이력이 새로 만들어졌을 가능성이 있으나 그 이유는 이 자료로 알 수 없습니다.

**D10. 학습 지시문 처리 (불일치).** 부록 A는 "각 학습 에피소드의 지시가 바꿔 쓰기 집합에서 무작위로 뽑힌다"고 씁니다. `collect.py`는 에피소드마다 `instructions/episode<N>.json`에 `seen` 전체(3개 안팎)를 저장하고, `lerobot_convert.py`는 기본값으로 **지시 변형마다 궤적 복사본**을 만듭니다(`--first-instruction-only`로 하나만 선택). 그러면 과제당 데이터가 변형 수만큼 복제되어 에피소드 수 3,750이 프레임 단위에서는 약 3배(Scene 2의 두 과제는 5배)가 되고, 같은 배치에서 한 에피소드가 서로 다른 문장으로 세 번 학습됩니다. 표 9의 스텝과 배치(π0.5 32 x 20,000 = 640,000 샘플)가 어느 쪽 설정이었는지는 논문에 없습니다.

**D11. 지시 변형 대조의 재구성 (불일치/빈칸).** 표 3의 변형 1/3/5는 "총 지시 변형 수"입니다. 공개된 Scene 2 지시 JSON은 14개 과제가 3개, 2개 과제(`pickup_red_cylinder`, `pickup_blue_cylinder`)가 5개라(합 52) 1개와 균일한 5개 조건은 이 파일만으로 만들 수 없습니다.

**D12. 학습 설정 (빈칸/불일치).** 저장소의 학습 코드는 π0.5뿐입니다. 표 9의 π0.5는 배치 32, 20,000 스텝, 나머지 8개 모델은 해당 설정이 없습니다. `pi05.py`의 기본값은 스텝 20, 배치 8, FSDP 4(짧은 시험용)이고 `action_horizon=50`, 샘플링 10 단계, 전체 파라미터 미세조정(`gemma_2b`, `gemma_300m`), `adapt_to_pi=False`, 델타 관절 행동, LeRobot FPS 17, 이미지 640 x 480으로 변환합니다. `protocol.yml`의 카메라는 D435 3대입니다. RoboTwin 기준 커밋은 `6dde57155eafa3e4ebf6ad1f93a7cf7d5d41a755`로 고정됩니다.

**D13. 논문 결과의 재현 코드 (미공개).** 표 1–3과 부록 D·E의 집계 스크립트, 빈 언어 π0.5 대조(표 1의 행), Qwen-GR00T, QA 공동학습 데이터와 코드, LangForce, CFG 설정, VQA 프로브 채점, 실로봇 코드는 저장소에 없습니다. 저장소 `docs/assets/data/results.*`는 표 1의 칸 값만 담고 있고(03 §1.1), 과제별, 시행별 결과 파일이 없습니다.

**D14. 평가 단위 정의의 일치 (일치).** CR의 과제 매크로 평균(`summarize()`의 `task_macro`), 집기류 IS/ES ≥ 0.8 규칙, "전체 5,540회"가 README와 코드에서 서로 맞습니다. `summarize()`는 과제 매크로(`completion_rate`)와 에피소드 미시 평균(`episode_micro_completion_rate`)을 함께 저장합니다. 과제당 시행 수가 같으면 두 값은 같습니다.

**D15. 개수 (일치).** 학습 과제 75, 지시문 변형 229, 평가 과제 554, 학습 에피소드 3,750, Scene 2의 800이 코드와 README에서 산술적으로 맞습니다(03 §6).

**D16. 위치 변동 (작은 차이).** 논문은 같은 배치에서 물체마다 1–2 cm의 무작위 변동이라고 합니다. 코드는 Scene 1에서 물체별 ±1.5 cm에 y 방향을 한쪽으로 제한하고, Scene 2에서 기본 ±1 cm와 y 한쪽 제한입니다. 범위 안이지만 방향 제한은 논문에 없습니다.

**D17. 프로젝트 사이트와 사이트용 PDF (참고).** README와 `docs/site-config.js`가 가리키는 프로젝트 페이지는 2026-11-26 기준 확인하지 못했습니다. 저장소 `docs/`는 그 페이지의 원본이며, `docs/downloads/robofollow-paper.pdf`는 arXiv v1과 세 곳이 다릅니다(`01` §0).

## 4. 구현 가능성 (이 맥: Apple M4 Pro, 약 24 GiB, MPS, CUDA 없음)

**결론: 논문 수치의 재현은 이 맥에서 불가능합니다. 표 재계산, 점수 규칙의 정적 대조, 평가 과제 목록의 정적 집계는 끝냈고, 같은 현상을 자작 소형 환경에서 다시 만드는 것만 조건부로 구현할 수 있습니다.**

### 4.1 막히는 곳

| 구성 요소 | 이 맥에서 | 근거 |
|---|---|---|
| RoboTwin 시뮬레이션, 전문가 시연 수집 | 불가 | 저장소 전제가 Linux, CUDA GPU, SAPIEN, cuRobo. macOS 렌더링 지원은 확인하지 못함(미확인) |
| 데이터셋 사용 | 조건부(다운로드 승인 후) | 합계 약 40.4 GB(Hugging Face API, 파일 15,158개). 받지 않음 |
| 모델 미세조정(π0.5 20,000 스텝 x 배치 32 등 9개 모델) | 불가 | GPU 학습과 JAX/OpenPI, 대형 사전학습 가중치 |
| 평가 5,540회 x 9개 모델 | 불가 | 시뮬레이터와 모델 추론이 모두 CUDA 전제. 시행당 최대 500 목표 실행, 시간은 측정하지 않음 |
| 완화 기법(Qwen-GR00T, LangForce, CFG) | 불가 | 구현과 설정이 공개되지 않음(D13) |
| 실로봇 파일럿 | 불가 | 하드웨어 |

### 4.2 이 맥에서 이미 한 것과 할 수 있는 것

- **완료:** 표 1–3, 부록 표 10, 엔트로피 산술의 재계산(`analysis/recompute.py`, 수 초, numpy와 scipy), 사이트 CSV 대조, 코드의 점수 규칙 정적 대조, 평가 과제 수의 코드 집계.
- **가능(조건부, 새 설치 없음):** mujoco 4.0과 torch 2.15가 이미 설치되어 있어 자작 2D 또는 MuJoCo 테이블탑에서 "관계로 물체 고르기" 과제와 L0–L3 분할, 언어 없음 대조, 단계 점수를 구현해 작은 정책(MLP 또는 소형 CNN + 텍스트 임베딩)의 L0 대 L1–L3 하락을 재 볼 수 있습니다. 이것은 RoboFollow의 수치를 재현하는 것이 아니라 같은 현상이 작은 모델에서 나오는지의 확인입니다. 노력 1–2주(추정, 측정 전).
- **평가 과제 목록의 정적 열거:** 평가 과제 이름과 지시문은 `--list`가 아니라 소스를 ast로 읽어 만들 수 있습니다(공식 코드는 import하지 않음). 노력 반나절.

### 4.3 CUDA 기기가 있을 때의 노력 (추정, 측정 없음)

| 단계 | 노력 |
|---|---|
| RoboTwin 설치, 자산, cuRobo 빌드 | 1–2일 |
| 데이터: HF에서 40 GB를 받거나 전문가 시연 3,750개를 새로 수집 | 받기 반나절, 수집은 시간 미확인 |
| π0.5 한 모델 미세조정(표 9: 배치 32, 20,000 스텝) | GPU 시간 미확인. 변환과 통계 계산 반나절 |
| 평가(한 모델 5,540회) | 시간 미확인. 시행당 정책 호출 최대 10회와 TOPP 실행 |
| 나머지 8개 모델 | 어댑터가 없어 모델마다 수일(추정) |
